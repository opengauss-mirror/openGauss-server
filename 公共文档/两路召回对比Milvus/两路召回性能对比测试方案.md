# openGauss HybridRecall vs Milvus Hybrid Search 两路召回性能对比测试方案

- 状态：方案（待执行），2026-09-05 起草
- 对比对象：openGauss 7.0.0-RC3 `Hybrid Recall` 算子（分支 `backup/feature-hybrid-recall-stacked-20260903`，HEAD `8f2410d20d4e`）× Milvus v2.6.22 standalone `hybrid_search()`（dense HNSW + 内置 BM25 sparse + RRFRanker）
- 双向判定口径继承《两路召回调研.md》§7/§8（Oracle 26ai 受控测试先例）：**方向一：相同召回质量比性能；方向二：相同性能预算比召回**
- 性能口径与 P3-7a（HNSW 10 万行标定，串行 P50 899 ms / 并行 643 ms）保持可比

## 1. 测试目标与边界

**比什么**：同为"文本 BM25 路 + 向量 HNSW 路 + RRF 融合"的两路召回，在**同机、同数据、同参数、同 K/候选预算**下的：

1. 端到端查询延迟（P50/P95/P99，单并发逐条计时）
2. 吞吐 QPS（并发 1/4/8）
3. 检索质量（recall@10 对暴力 ground truth；scifact nDCG@10 对 qrels）
4. 附带成本：数据导入吞吐、索引构建时间、索引磁盘大小、内存/CPU 峰值
5. openGauss 自身串行/并行收益（off vs force，对照 P3-7a 的 28.50%/44.24%）

**不比什么 / 差异声明**（报告必须携带）：

- openGauss 是关系库内算子（MVCC/SQL/事务/权限完整），Milvus 是专用向量数据库；本对比回答"数据库原生两路召回 vs 专用向量库两路召回"的差距，不评判架构优劣。
- 融合能力差异：openGauss 支持加权 RRF（`weights`），Milvus `RRFRanker` 无权重、`WeightedRanker` 是归一化分数加权而非加权 RRF → 主口径统一用**均等权重 RRF（rrf_k=60）**，加权档只在 openGauss 侧附加测并标注。
- 两系统 BM25 分词/打分公式、HNSW 实现不同 → **不要求结果逐项一致**，质量差异全部通过 recall/nDCG 度量。
- 单机 WSL2 环境，非生产 SLA 数据；结论限定在测试规模（≤10 万行主口径）。

## 2. 语义对齐矩阵（公平性的核心，逐项对齐并留痕）

| 维度 | openGauss HybridRecall | Milvus 2.6 | 对齐策略 |
|---|---|---|---|
| 文本路 | 内置 `bm25` 索引（`USING bm25(content)`） | `Function(BM25)` + sparse vector 字段，analyzer=standard | 全英文数据集弱化分词差异；S1 各跑 1 条样本查询记录双方 tokenize 行为差异进 evidence |
| 向量路 | `hnsw(embedding vector_cosine_ops)`，768 维，向量 L2 归一化 | `HNSW` index on dense field，metric=COSINE（或 IP+归一化，取一致者） | 同数据同向量；归一化后 COSINE/IP 等价 |
| HNSW 参数 | S1 探测 `CREATE INDEX ... USING hnsw(...) WITH (...)` 可暴露的 M/efConstruction/ef；可设则设 M=16、efConstruction=200、ef(search)=100；不可设则记录默认值并在报告标注"默认档" | `index_params={"M":16,"efConstruction":200}`，search `ef=100` | 两档：**默认参数档**（各自开箱默认，主报告）+ **对齐参数档**（能对齐多少对齐多少，附录） |
| 融合 | `{"rrf_k":60, "weights":[1,1]}` | `RRFRanker(k=60)` | 均等权重，rrf_k=60 |
| 每路候选 | options `text_candidates` / `vector_candidates` | 两个 `AnnSearchRequest.limit` | 主档 100/100；附档 1000/1000（与 P3-7a 可比） |
| 最终 K | `LIMIT 10` | `limit=10` | 固定 10 |
| 查询向量 | `query_vector` option 预注入，跳过 embedding 服务 | 客户端直接传预计算向量 | 两边都离线预计算，计时不含 embedding |
| 一致性级别 | 单机可重复读 | Milvus `Bounded`（默认）；数据静态、load 后无写入 | 记录配置即可 |
| 返回内容 | `SELECT id`（score 仅冒烟时取） | `output_fields=["id"]` | 传输量最小且相同 |
| 客户端 | Python + psycopg2（本地 trust 免密直连 127.0.0.1:55440） | Python + pymilvus（127.0.0.1:19530） | 同一 harness、同样逐条端到端计时（含网络往返、不含连接建立） |

**openGauss 侧查询模板**（marker 语法见《openGauss_文本与向量两路召回特性使用指南.md》§3.4）：

```sql
CREATE EXTENSION IF NOT EXISTS ogai;
SET enable_hybrid_recall = on;
SET hybrid_recall_parallel_mode = force;   -- 串行档改 off，自动档 auto

PREPARE hrq(text, vector, int, int) AS
SELECT id FROM hybrid_bench_docs
ORDER BY ogai.hybrid_rrf_marker(
         id, content, embedding,
         $1, $2,
         jsonb_build_object('text_candidates', $3, 'vector_candidates', $3,
                            'rrf_k', 60, 'weights', '[1,1]')) DESC
LIMIT 10;
EXECUTE hrq('query text', '[...768 floats...]::vector', 100, ...);
```

**Milvus 侧查询模板**：

```python
from pymilvus import AnnSearchRequest, RRFRanker
req_dense = AnnSearchRequest(data=[qvec], anns_field="dense",
    param={"metric_type":"COSINE","params":{"ef":100}}, limit=100)
req_sparse = AnnSearchRequest(data=[qtext_embedded_by_bm25_function], anns_field="sparse",
    param={"metric_type":"BM25"}, limit=100)
res = client.hybrid_search("hybrid_bench_docs", reqs=[req_dense, req_sparse],
                           ranker=RRFRanker(60), limit=10, output_fields=["id"])
```

（sparse 路查询文本经集合上定义的 BM25 Function 自动编码，客户端传原始文本。）

## 3. 环境与资源口径

机器：WSL2，20 核，**7.8 GiB 内存（硬约束）**。

| 项 | 约定 |

| Milvus | podman 部署 `milvusdb/milvus:v2.6.22` standalone（embed etcd + local storage 单容器模式），卷放数据盘 `~/data/programs/milvus/volumes`（照 oracle 模式）；官方建议 ≥8 GiB 可用内存 → 用降配 `standalone.yml`（压 queryNode 内存 quota），资源参数快照进 evidence。**严禁与 oracle 容器同时在线** |
| 执行顺序 | 两系统**交替执行**（AB 轮换，每 60 查询换边），禁止先全跑 A 再全跑 B；单并发延迟轮次内也按 ABBA 排序抵消漂移 |

## 4. 数据与查询负载

### D1 scifact 质量集（真实文本）

- 数据：`.codex_tmp/oracle26ai_hybrid_bench_20260831/`（docs.tsv 5183 篇 / queries.tsv 1109 / qrels.tsv 339）
- 向量：确定性伪随机（固定种子，按 doc 聚类生成簇结构），768 维 L2 归一化 —— 性能不依赖语义真实向量；**nDCG 主要反映文本路 + 融合相对收益**，此限制在报告标注
- 用途：两系统融合 vs 各自单路的 nDCG@10 / recall@10；不作为主性能集（5183 行延迟以固定开销为主）

### D2 10 万行合成集（性能主集，与 P3-7a 规模可比）

- 文本：zipf 词表 + 200 个主题簇词袋生成英文伪文档（均值 ~120 词），保证 BM25 有区分度
- 向量：`emb = normalize(cluster_center[c] + N(0, 0.1)^768)`，768 维；查询向量 = 簇中心 + 更小扰动 → 两路天然有部分 overlap，RRF 融合有意义
- 查询：1000 条固定（同簇词采样文本 + 对应簇扰动向量），种子固定可复现
- 规模预算：dense 原始 10万×768×4B ≈ 293 MB，加 HNSW 图与 sparse，两系统各 < 1 GB，7.8 GiB 可承受

### D3 100 万行（可选扩展档，默认不执行）

- 7.8 GiB 内存下两系统索引无法并存，需降维（如 256 维）或加内存；单独立项评估后再启动，不阻塞主报告

### Ground truth 与质量度量

- ANN 路 recall：SQL 暴力全表余弦 top-100（`ORDER BY embedding <=> qvec LIMIT 100` 的 exact 距离计算）作为 GT，校验 HNSW 单路 recall@100 ≥ 99% 后才开测（两系统同标准）
- 文本路：BM25 索引本身是精确排序，信任索引；抽样 20 条与暴力打分比对
- 融合 GT：两路精确 top-100 经相同 RRF(k=60) 公式离线计算 → 融合 recall@10
- D1 质量：nDCG@10（qrels 339 条）

## 5. 测试矩阵

| 组 | 变量 | 取值 | 指标 |
|---|---|---|---|
| A 单并发延迟 | 系统 × openGauss模式 × 候选 | {openGauss, Milvus} × {off, force, auto} × {100, 1000} | 预热 5 + 每配置 100 查询，客户端逐条端到端计时，P50/P95/P99 |
| B 单路基线 | 系统 × 单路 | {BM25-only, ANN-only}（openGauss 用 marker 单路权重 [1,0]/[0,1]，Milvus 用单 `search()`） | 同 A；用于证明互补性与融合开销 |
| C 并发吞吐 | 系统 × 并发 | {1, 4, 8} × 两系统（openGauss 取 A 中最优模式） | 固定 60 s 或固定 1000 请求，QPS + P95；失败/错误率必须为 0 |
| D 质量 | 系统 × 融合/单路 | D2 recall@10（融合 GT）；D1 nDCG@10 | recall/nDCG 表 |
| E 构建成本 | 系统 | 导入吞吐、HNSW+BM25(sparse) 索引构建时长、索引磁盘大小 | 表 |

预算估计：A 共 12 配置 × ~1 min、C 6 轮 × 1 min + 预热、D/GT 计算一次性 ~30 min、E 随 S1 采集。

**判定标准**：

1. 主判定（方向一）：在 recall@10 差 ≤ 2 pp 的质量档内，比较端到端 P50/P95 比值（含单并发与并发 8 两档）
2. 次判定（方向二）：在 P95 预算相近的配置间，比较 recall@10 差
3. openGauss 并行收益须复现 P3-7a 量级（P95 降 ~40%），作为本测试方法有效性的内部校验锚点
4. 结论表述模板："同等质量（recall@10 X vs Y）下，openGauss P95 = A ms vs Milvus B ms（比值 R），并发 8 时 QPS = …"

## 7. 风险与已知坑

1. **debug 构建失真**（最高优先）：开测前必须 `select version()` 确认无 `debug on`；P3-7a 的 release 定向构建记录是先例。
2. **内存 7.8 GiB**：oracle 容器不停必 OOM；Milvus 降配后若仍 OOM，降 D2 到 5 万行并标注；D3 冻结。
3. **psycopg2 连 openGauss**：本实例本地 trust 免密，无 sha256 认证坑；若异常备选 `py-opengauss`。
4. **WSL2 计时噪声**：所有对比走交替执行 + ≥100 样本 + P95 口径；报告注明环境。
5. **marker 硬约束**：顶层单表只读 SELECT、唯一 `ORDER BY marker DESC`、正有限 LIMIT、无 OFFSET/JOIN/子查询；options 里 candidates、K 不得超 GUC 上限（单路 1000、final 100）——候选档 1000 是上限值，可用。
6. **Milvus analyzer**：对连字符/句号切分与 openGauss 分词不同，英文数据影响小，S1 留痕即可。
7. **oracle 容器**：只 `podman stop`，**严禁 `podman rm oracle26ai`**。
8. 分支纪律：backup 分支严禁 reset/checkout 到 origin/main；构建只用 `opengauss_build_install_restart.sh`。
