## 1. 测试数据集介绍

### 1.1 D1：SciFact 真实文本质量集

| 项目 | 内容 |
|---|---|
| 文档 | 5,183 篇真实英文科学文档 |
| 查询 | 1,109 条 |
| qrels | 339 条；其中 300 条查询有人工相关性标注 |
| 向量 | 768 维 float32、固定种子的词袋随机投影，按词频加权求和后做 L2 归一化；不是语义模型 embedding |
| 主要指标 | nDCG@10，辅助观察 recall@10 和小表固定开销 |
| 用途 | 检查真实文本上的 BM25 与融合质量；不作为主要性能集 |

D1 的文本是真实语料，但向量不是语义模型生成的 embedding。因此，D1 的 nDCG 更能反映文本检索和融合排序的相对表现，不能把它解释成真实语义向量模型的端到端效果。D1 最长正文为 10,256 字节，也不能直接套用 D2 的“正文与向量都 PLAIN”布局。

SciFact 历史测试性能及已验证优化收益见 §4.4；2026-10-13 投影优化前的同期复测见 §4.5.2，新代码状态见 §4.5.4，不能把历史实验拼接为最新等质量 PK。

## 2. 和 Milvus 对比的原始状态

### 2.1 2026-09-05 初始基线

原始质量对齐档为 openGauss `ef=400`、Milvus `ef=100`，两路候选均为 100。原始结果如下：

| 指标 | openGauss 原始状态 | Milvus 原始状态 | 原始结论 |
|---|---:|---:|---|
| D2 单查询 P50 | 5.0 ms | 2.7 ms | Milvus 约快 1.9 倍 |
| D2 单查询 P95 | 7.8 ms | 3.7 ms | Milvus 约快 2.1 倍 |
| D2 单查询 P99 | 9.3 ms | 4.2 ms | Milvus 约快 2.2 倍 |
| D2 并发 8 QPS | 883 | 977 | openGauss 低约 9.6% |
| D2 并发 8 P50/P95 | 8.8/12.5 ms | 7.8/12.0 ms | Milvus 略优 |
| D2 BM25 单路 P50 | **0.54 ms** | 2.28 ms | openGauss 约快 4.2 倍 |
| D2 ANN 单路 P50 | 2.70 ms（ef=400） | 2.41 ms（ef=100） | 同质量下接近，Milvus 略优 |
| D2 融合 recall@10 | **0.8834** | 0.8790 | openGauss 高 0.44 个百分点 |
| D1 融合 nDCG@10 | **0.4951** | 0.4338 | openGauss 质量更高 |
| D1 融合 P50/P95 | 10.8/22.0 ms | 2.8/4.2 ms | 小表上 openGauss 明显更慢 |

原始状态并非“所有方面都比 Milvus 差”：openGauss 的 BM25 单路、D2 融合 recall、D1 nDCG 和并发扩展性已有优势；真正落后的核心是单请求端到端延迟和尾延迟。

### 2.2 原始装载与索引记录

| 项目 | openGauss | Milvus | 可比性说明 |
|---|---:|---:|---|
| D2 导入 | COPY 12.7 s | insert+flush 18.8 s | openGauss 导入更快 |
| D2 建索引 | BM25 38.2 s + HNSW 636.4 s | `create_index` 阶段记录 6.1 s | 不能直接用 636.4/6.1 得出倍数 |
| openGauss 索引大小 | BM25 275 MB + HNSW 410 MB | 原报告另存 stats | 统计边界不同 |

Milvus 在插入前已经提供索引参数，索引工作可能与装载阶段重叠，旧脚本的 flush 与等待边界也不完整。因此，“Milvus 只用 6.1 秒完成同等建索引”没有被当前证据证明；后续若比较构建性能，必须重新测量从空数据到 collection 可查询的完整时间。

### 2.3 复核后确认的主要根因

1. **HNSW 上层导航质量缺陷是第一大根因。** 原实现每层下降只保留 1 个候选，200 个主题簇的数据上容易整簇走错，迫使 openGauss 用 4 倍 `ef` 才达到相同召回，直接放大向量路成本。
2. **并行 worker 未继承 datavec 搜索 GUC。** `force` 模式实际没有使用主会话的 `hnsw_ef_search`，导致并行结果质量下降；这是正确性问题，也让早期并行性能对比失真。
3. **原表向量走 EXTERNAL TOAST，热路径存在外置取回。** 火焰图中 `heap_tuple_untoast_attr` 含子调用约占 19.31%，其下主要是 `toast_fetch_datum`；没有证据表明当时主要在执行压缩解码。问题是外置值获取及相关 buffer/索引访问，不应简化成“解压算法慢”。
4. **小候选下临时 stream worker 的固定成本过高。** 每次 `vector`/`force` 查询会创建并退出 1/2 个普通 stream worker；100+100 小候选时，并行节省的支路重叠不足以覆盖启动和通信成本，所以最终获胜路径仍是串行 `off`。
5. **BM25 初始批量默认过小。** `bm25_topk=5` 为取得 100 个候选会多次扩批，重复候选组织和页面访问。
6. **火焰图后期确认瓶颈已转移到 HNSW 图遍历。** 消除 TOAST 后，慢查询增加的 CPU 主要落在 HNSW 元素页随机 buffer/page 访问、邻接展开和向量内积，而不是最终 RRF 排序。

以下旧解释已经被复核否定，不应继续作为优化依据：`Fusion Time=0.006 ms` 不代表全部融合成本；410 MB HNSW 并未超过实查为 1 GB 的 `shared_buffers`；Milvus 的 6.1 秒不能直接解释为纯异步声明；出现 detoast 包装函数也不等于正在进行压缩解码。

### 3.2 已证明有效的参数与测试布局优化

| 优化 | 实测效果 | 限制 |
|---|---|---|
| `bm25_topk` 从 5 调到 100 | 早期 D2 P50 3.7801→3.2419 ms（-14.2%），P95 5.2651→4.2460 ms（-19.4%）；D1 P50/P95 分别下降 15.2%/16.5%。最终栈补测再次确认：默认 5 的 P50=3.2197 ms，比同期 Milvus 慢 22.29%，而调优主档 100 的 P50=2.3410 ms，比同期 Milvus 快 11.11% | 当前是会话/测试配置，没有全局硬编码；少数同分结果顺序变化，但 D2 recall 和 D1 nDCG 未变 |
| D2 `embedding` 与 `content` 均使用 PLAIN 并真正重存 | TOAST 数据从 409.60 MB 降到 0；复核中 P50 3.2997→2.6093 ms；火焰图不再出现 `toast_fetch_datum`/`pglz_decompress` | 新表与原表的 HNSW 图不同，因此不是“同一物理索引”的纯存储 A/B；D1 长正文不能照搬 |
| 新SciFact99%会话keeper 2→4MiB | 旧二进制同参数正反序诊断中线程轻缺页约261.7→129.0/请求，P50约4.264/4.273→3.985/4.023ms；8MiB没有进一步改善 | 只调该档会话，不改默认0；其余轻缺页由visited容量补丁继续消除，代码与参数收益分开计 |

只把 `embedding` 改成 PLAIN 并不好：它会把正文推向压缩/外置，实测 P50 反而从 3.2042 ms 退化到 4.8439 ms。D2 的正文只有约 839 字节，两列合计仍能装入 8 KB 页，因此 all-PLAIN 才有效。该结论说明存储布局必须按整行分析，不能机械地把单列设为 PLAIN。

PLAIN 对照使用隔离新表，为每张新表新建了对应 HNSW，因为索引中的 heap TID 绑定所属表；这是实验隔离需要，不是 `ALTER ... SET STORAGE` 本身要求重建旧索引。后续 HNSW 代码优化一直复用已经建好的 all-PLAIN 表和索引。

### 3.3 局部有效但不是最终获胜路径的工作

- 开启既有线程池已验证真实复用OS线程，但仍重建任务session，且普通连接也会进入会话线程池。本轮ON配置的SciFact99观察落后；不是默认获胜配置，已恢复原OFF设置，见§4.5.17。
- task stream 批大小由 100 降至 16，并增加仅向量支路并行的 `vector` 模式（纯分支 `891941e164`，原堆叠提交 `83ae60ab9f`），将首批交付时间约从 2.9 ms 降到约 1 ms，并验证输出与串行一致；但 100+100 小候选的端到端性能仍不如串行 `off`，所以最新对标没有依赖该模式。
- vector 支路私有 `MinimalTuple` 缓冲与回放（纯分支 `17f2a92b93`，原堆叠提交 `6c0886e8e2`）提供了后续并行实验基础，但没有独立证明加速，不能单独计入最终性能收益。

### 3.4 已验证无效并回退的方向

| 方向 | 结论 |
|---|---|
| 只内联 detoast 快速检查 | 只能改变采样栈帧归属，没有稳定净收益，已回退 |
| 四累加器 AVX 内积 | 没有火焰图收益，并产生 Top-100 浮点排序漂移，已回退 |
| 合并 `HnswCandidate` 与 pairingheap 分配 | 干净窗口未优于保留版，收益上限很小，已回退 |
| 全局关闭 `hnsw_iterative_scan` | 无过滤时快，但过滤用例可从应返回 10 行退化为 0 行，只能用于性能上限诊断 |
| 只切换/强求 SQL Bypass | 已确认真实走过 Bypass，但 P50/P99 没有稳定大幅收益；不是最后瓶颈 |
| 扫描级小型页 LRU、邻接批排序 | 页访问实测命中仅约 4%–10%，批内也没有可合并的重复页，不值得保留 |
| HNSW early-stop 阈值 | 当前代表查询没有稳定触发或收益，不能作为默认优化 |

### 4.1 95% 与 99% 严格等召回的同期 ABBA 正式结果

扫描证据为[openGauss 95% 精扫](验证/Pareto寻优/openGauss召回95候选精扫_D2.json)、[Milvus 95% 精扫](验证/Pareto寻优/Milvus召回95候选精扫_D2.json)、[openGauss 99% 临界 ef 精扫](验证/Pareto寻优/openGauss召回99临界ef精扫_D2.json)和[Milvus 99% 临界 ef 精扫](验证/Pareto寻优/Milvus召回99临界ef精扫_D2.json)。旧 `0.8802` 等召回 ABBA 与固定 100+100 结果仍作为历史复现和诊断证据保留，但都使用有同分偏差的旧单参考，不再作为公平 PK 主结论。

### 4.2 默认 `bm25_topk=5` 的最终栈补测

这里的 `bm25_topk` 是 openGauss BM25 **内部初始搜索批量**，不是用户最终返回 Top-K，也不是每路候选数。以下两档都仍然是最终 Top-10、BM25/HNSW 各 100 个候选；区别只是 `bm25_topk=5` 会按 5/10/20/40/80 多次扩批，而 `bm25_topk=100` 可按当前候选预算一次取足。

为回答默认值下是否仍领先，使用同一最终二进制、同一 all-PLAIN 表和同一 HNSW 索引补做了 `bm25_topk=5` 的两轮同期 ABBA，证据见[默认 topk=5 同期 ABBA 汇总](验证/BM25批量对照_最终栈_topk5_同期Milvus_ABBA/summary.json)。这组质量值使用旧单参考，只保留为内部批量诊断，不与 4.1 的新双参考高召回结果横向拼接：

| 指标 | openGauss，`bm25_topk=5` | Milvus 同期 | openGauss 相对 Milvus | 结论 |
|---|---:|---:|---:|---|
| P50 | 3.2197 ms | 2.6329 ms | **慢 22.29%** | Milvus 领先 |
| P95 | 4.5781 ms | 3.4806 ms | **慢 31.53%** | Milvus 领先 |
| mean | 3.6997 ms | 2.7148 ms | 慢 36.28% | 受首轮换页放大 |
| 聚合 P99 | 12.4700 ms | 4.2502 ms | 不作正常稳态定量 | openGauss 首轮有明显换页干扰 |
| 单连接 QPS | 269.68 | 367.40 | 低 26.60% | 聚合值同样受首轮换页影响 |
| recall@10 | **0.883** | 0.879 | 高 0.004 | 质量仍高 0.4 个百分点 |

P50 的结论不依赖异常长尾：两轮 openGauss/Milvus 分别为 `3.2174/2.6248 ms`、`3.2220/2.6405 ms`，openGauss 两轮都慢约 22%。P95 也两轮均输。第一轮 openGauss 正式窗口出现 60 页 swap-in、36 次 major fault，令 P99 升至 30.45 ms；即使只看无 swap-in 的第二轮，P99 仍为 openGauss/Milvus=`5.0816/4.4529 ms`，openGauss 慢约 14.12%。

因此，“当前已经领先 Milvus”明确依赖于让内部 BM25 初始批量匹配文本候选预算：新 95%/99% 主档分别为 55/100，而不是实例默认的 5。该设置不改变用户看到的最终 Top-10。最终报告必须同时列出“默认配置诊断”和“双方独立寻优后的高召回主档”，不能让读者误认为默认值也领先。

### 4.4 SciFact（D1）测试性能与已验证优化收益

本节参照 D2 汇总补充数据、测试条件和变化比例，但证据性质不同：这里只汇总 2026-09-05～09-06 的已有实验，**本节不是最新代码的 SciFact 同期复测**。从归档逐查询样本补算的批量对照 P99 也不是新增性能测试；2026-10-13 随后实际执行的最新同期复测单列于 §4.5.2。

本节对应测试数据与口径：

- 数据来源：SciFact 的真实英文科学文献，5,183 篇，使用标题与摘要；查询共 1,109 条，qrels 共 339 条相关性记录，质量评估使用其中 300 条有标注查询。SciFact 是公开学术基准，但本项目的向量生成与数据库性能测试方式是自定义的。
- 向量：768 维 float32；文本词袋经固定种子随机投影、词频加权求和后做 L2 归一化，两系统使用相同文档与向量，不是语义模型 embedding。数据生成依据见[生成脚本](../../deliverables/hybrid_vs_milvus_bench/gen_data.py)和[参数快照](../../deliverables/hybrid_vs_milvus_bench/data/meta.json)。
- 检索：BM25 + HNSW 两路召回，最终 Top-10、等权 RRF `k=60`，以下两组实验都固定两路各 100 个候选。`bm25_topk` 是 OG 文本路内部初始批量，不是最终 Top-K；批量对照没有减少候选数。
- 计时与质量：客户端端到端时延，包含发送、执行和结果取回，不含连接建立与向量生成。nDCG@10 使用人工 qrels 评估排名质量，越高越好；它不是 D2 的双参考 recall@10，也不是“召回达到 95%/99%”。
- 存储布局：使用原 D1 表，向量为 EXTERNAL、正文允许 TOAST；不是 D2 的 all-PLAIN 布局。D1 最长正文 10,256 字节，不能直接把正文与向量都设为 PLAIN。

#### 4.5.16 修改前的并行瓶颈诊断（2026-10-15，历史记录）

本轮保持`b47f4fb9a5`及原Release/O2二进制不变，用worker完整CPU图、轻缺页事件图和函数入口/返回时间线核对。FORCE确实每请求有两个不同OS worker，VECTOR一个，无fallback，所有诊断请求的有序ID与冻结结果一致。

同一时钟下，从服务端Bind入口到Sync返回，SciFact95 FORCE的636次请求平均为**2.907ms（首worker开始Run前）+3.750ms（worker Run包络）+2.579ms（末worker结束Run后）=9.235ms**；D2 95 FORCE的582次请求为**2.726+1.433+2.545=6.704ms**。这是查询子集的阶段诊断，不是新全量性能表；Run包络含传输/等待，不等于纯检索CPU。两组追踪窗口主机swap-in/out/major-fault均为0。

确认了四个实现原因：

1. `StreamNodeGroup::deInit()`即使已经判定可以退出，也会继续执行`pg_usleep(1000)`。两组FORCE及480次VECTOR请求，每次都在此循环睡两次，阶段均值2.24～2.28ms；它在协议Sync/销毁阶段，单看算子EXPLAIN或CPU火焰图容易漏掉。
2. 当前非线程池模式每请求重建worker/session/GUC/数据库环境。启动提交调用本身约0.14ms，不是全部启动耗时；固定约1ms周期采样中，初始化占完整进程CPU样本36.53%，退出/清理8.48%。
3. HNSW工作区及buffer提示缓存属于session，短命worker不能像串行持久会话那样跨请求保留。无perf的SciFact95完整查询窗口中，FORCE约1807次minor fault/请求，串行接近0；是轻缺页/内存生命周期问题，不是已经证明磁盘或swap慢。
4. BM25 rank-only优化只接受直接`Limit → IndexScan`，没有传入Stream worker，导致并行仍构建原始分数表、回表取正文。正文解压仅占本次并行CPU样本约1.49%，不是主要差距，更不是HNSW距离循环重新退回detoast。

因此当时AUTO选串行有实测依据，但不能推出“并行没有优化空间”。本节诊断时收尾等待改进尚未实施；后续sleep/worker修复及成本修订见§4.5.17，串行核查见§4.5.18。轻量worker/会话复用及并行rank-only仍需研究，仅打开线程池不是完整修复。

完整边界、原始计数、测量扰动排除和源码位置见[交接§0.37](交接文档_继续优化.md)；证据见[机器审计](验证/并行瓶颈分析_20261015/diagnosis_audit.json)、[并行CPU图](验证/并行瓶颈分析_20261015/SciFact95_force_cpu_1ms/attributed_cpu.svg)、[SciFact阶段时间线](验证/并行瓶颈分析_20261015/SciFact95_force_timeline_deinit/timeline_summary.json)。CPU采样窗口存在少量主机换页，只用于内部定位，不冒充正式干净PK；时间线与表列无perf控制窗口另有独立环境计数。
