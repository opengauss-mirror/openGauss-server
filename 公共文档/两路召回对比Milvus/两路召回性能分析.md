## 最新结论：距离直达、延迟 discarded 与同页邻接预取（2026-09-07）

当前运行版不是 §0.14 所述已回退的 `vector.cpp` 局部 detoast 快检，而是三项经重新编译、安装、回归和同索引验证后保留的 HNSW 优化：

1. 对内置 vector IP/cosine opclass 的 HNSW 距离计算直接调用现有 `VectorInnerProduct`，跳过每个已访问节点的 fmgr、Datum 取参、重复 detoast 头检查和结果 Datum 转换；特殊编码、自定义 opclass及需要加载向量副本的路径保持通用实现。
2. 对首轮已计算距离、但未进入当前最佳结果集的 discarded 候选，只保存距离、索引位置和版本号，不立即复制 heap TID、邻接位置等完整元数据；首批有效结果满足 LIMIT 时不再处理，因过滤/MVCC 不可见导致不足时，才按距离顺序校验版本、补全元数据并继续搜索。这没有省略首轮元素页读取或距离计算，也不等价于不安全的全局 `hnsw_iterative_scan=off`。
3. 对同页的 HNSW element/neighbor tuple，在第一次持页锁时复制紧凑邻接 TID，展开候选时不再第二次 `ReadBuffer/LockBuffer`；非同页、版本/编码不匹配保留原回退。

最终源码差异位于 `hnswutils.cpp` 与 `hnswscan.cpp`；`vector.cpp` 无差异。最终安装二进制 SHA256 为 `3414c0dbaa5e10b037dccc25467ae344376c95a815fc83f281895986f2e997f4`，构建日志为 `/home/qiumc/data/code/cpp/openGauss-server/build_logs/incremental_20260907_151957.log`。

### 已否决路线与下一步

- 仅内联 `PG_GETARG_VECTOR_P`/detoast 快检：只是将采样从 callee 移到 caller，端到端净收益不可复现，已回退；
- 四累加器 AVX：现有核本已用 256-bit AVX，实验无火焰图收益且 Top-100 浮点排序漂移，已回退；
- 合并 `HnswCandidate` 与 pairingheap node 分配：正确性通过，但干净窗口没有证明优于当前保留版，且候选管理仅约 2% CPU，已回退；
- 全局关闭迭代续扫：可领先 Milvus P99，但过滤/MVCC 语义不成立，只保留为上限对照。

下一项高价值工作是先补 lazy discarded 和邻接预取的并发 VACUUM/UPDATE/DELETE 正确性门，然后研究降低元素页首次随机访问的布局或不可变读路径。扫描级小 LRU 已被实测约 4%–10% 命中率否决，不应重复实施。mmap/不可变存储可能减少元素页的 buffer 管理，但须先定义 pin/锁、VACUUM、并发更新、回收和内存上限。D1 长正文、并发吞吐及更多过滤选择率仍待单独验证。

### 0.3 TOAST 到底贵在哪：detoast 路径，不是解压热点

用户指出 detoast 和 PLAIN 方向后，已经只读核实两张表的实际属性：

| 表 | 行数 | embedding 类型/attstorage | content 属性 | heap / TOAST 主数据大小 |
|---|---:|---|---|---|
| hybrid_bench_d2 | 100,000 | vector(768) / `e`（EXTERNAL） | `x`（EXTENDED） | 87 MB / 391 MB |
| hybrid_bench_d1 | 5,183 | vector(768) / `e`（EXTERNAL） | `x`（EXTENDED） | 7640 kB / 20 MB |

两表每个向量的 `pg_column_size(embedding)` 都为 3076 字节；此口径对外置值不含恢复后的四字节 varlena 头，768 维完整向量约 3080 字节。表块大小实查为 8192 字节。`EXTERNAL` 不尝试压缩，但允许外置；`detoast` 同时涵盖取回外置数据和解压，不能把名字直接翻译成“正在解压”。[openGauss SET STORAGE 说明](https://docs.opengauss.org/zh/docs/latest/sql_reference/alter_table.html)

主样本可见调用路径：

```text
cosine_distance
  → heap_tuple_untoast_attr
    → toast_fetch_datum
      → heap_internal_toast_fetch_datum
        → systable_getnext_ordered → index_getnext
          → B-tree 查找 / TOAST heap 取块 / 缓冲页访问
```

以下全部以完整查询的 7,669 个样本为分母：

| 函数 | 包含子调用的 CPU 占比 | 函数自身 CPU 占比 |
|---|---:|---:|
| `cosine_distance` | 19.6897% | 0.3390% |
| `heap_tuple_untoast_attr` | 19.3115% | 0.0261% |
| `toast_fetch_datum` | 19.2854% | 0.0391% |
| `pg_detoast_datum`（独立可见栈帧） | 3.5859% | 3.5859% |
| `pglz_decompress` | 0 个样本 | 0 个样本 |

**“detoast 整段很贵”成立；“在执行压缩算法的解压”不符合本次证据。** `pg_detoast_datum` 在源码中先检查是否扩展值，再返回原指针或调用 `heap_tuple_untoast_attr`；优化后的调用栈可能不保留所有包装层。此处独立可见的 `pg_detoast_datum` 样本 275 个中，272 个属于 HNSW 搜索，不应拿它单独的 3.59% 代替 TOAST 取回路径的 19.31%，也不应把两者机械视作父子再相加。

进一步只取 `cosine_distance → toast_fetch_datum` 的 1,479 个样本：

| TOAST 子树中的热点 | 统计口径 | 占 TOAST 子树 | 占完整查询 |
|---|---|---:|---:|
| `systable_getnext_ordered` | 含子调用，索引取块主路径 | 69.78% | 13.46% |
| `BufferAlloc` | 含子调用，和上一行存在包含关系 | 26.30% | 5.07% |
| `buf_hash_operate<…>` | 函数自身，缓冲页哈希查找 | 15.62% | 3.01% |
| `_bt_check_natts` | 函数自身，B-tree 元组检查 | 9.40% | 1.81% |
| `[libc.so.6]` | 叶子，仅解析到库，不能全部归成 memcpy | 8.05% | 1.55% |
| `LWLockAttemptLock` | 函数自身，尝试获取轻量锁 | 5.75% | 1.11% |
| `PinBuffer` | 函数自身，固定缓冲页 | 5.14% | 0.99% |

这解释了为什么“最宽的 detoast 父函数”和“最大的自身热点 buf_hash_operate”可以同时成立。CPU 图中的锁函数耗时也不等于离 CPU 的锁等待时间。

### 0.4 PLAIN 的存储语义与实验设计（实际结果见 §0.8）

- 用户建议的方向正确：**向量实际以 PLAIN 内联存储后，读取它不再需要 TOAST 外置取数**。只是快速 detoast 检查可能仍会调用；不能将这种检查与外置 fetch 混为一谈。不是只改“表压缩属性”，也不是针对当前向量解压缩。
- `SET STORAGE` 只修改后续存储策略，不自动改写已有行。源码还会复用 UPDATE 中未改变的旧 TOAST 指针，因此不能笼统保证 `UPDATE SET embedding=embedding` 就能完成转换。
- 用户随后要求“继续”，已按先设置列属性、再导入相同数据、建立同参数索引的方式创建两张隔离对照表；原表保留。
- 768 维单向量约 3 KB，在当前 8 KB 页中有容纳空间；仍要核查整行尺寸。D2 正文全部为 839 字节，允许验证两列 PLAIN；**D1 最长正文为 10256 字节，不能将这个组合直接照搬到 D1**。
- 代价是主表更宽、每页容纳行数下降，可能改变 BM25 回表和缓存行为；它也不会消除 HNSW 索引内部的 BufferAlloc/图搜索。总体收益必须测，不能承诺直接节省整个 19.29%。
- 更通用的内核方向是：RRF 只需排名时，不要求向量子计划输出原始距离，避免为不使用的距离求值而读取整列。它与 PLAIN 大量收益重叠，不能把两者的预计收益累加。

### 0.5 BM25 批量收益已有 CPU 路径支持

同为 100/100 候选、ef=100、串行；下面仅列有效的用户态 CPU 样本占比。旧阶段毫秒估计已撤回，比例变化不能单独证明绝对 CPU 降幅：

| 路径 | 默认批量 5，样本占比 | 批量 100 复核，样本占比 |
|---|---:|---:|
| BM25 扫描 | 28.38% | 17.25% |
| HNSW 搜索 | 33.84% | 39.74% |
| 向量距离投影及取值 | 17.48% | 19.69% |

主要变化集中在 BM25 扫描，与初始批量 5 时反复扩展、组织候选和重复页访问的源码行为一致，支持先前独立批量试验中 D2/D1 P50 约 14%/15% 的改善。不是笼统把所有函数的百分比下降当成提速。

反而，BM25 下 `CreateExecutorState` 含子调用仅占全查询 0.339%、`BuildIndexInfo` 0.039%；内联可能令个别函数漏计，但目前没有理由把复用 EState 列为毫秒级首要突破口。候选扫描整体、分数映射/回表和不必要的正文处理比单盯初始化函数更值得看。

### 0.6 当前优化顺序和仍未完成的工作

1. **PLAIN 两种布局验证已经完成**，直接复用现有对照表。短正文 D2 两列 PLAIN 有收益；长正文要另行研究布局，不能强制无法放入单页的行内存储。
2. 实施层面考虑 **rank-only 向量子计划**，保留索引排序、过滤、MVCC/RLS/权限和用户真正需要的 payload。原布局候选向量 TOAST 取值成本已被全 PLAIN 消除，不能再预报叠加同一收益；对原表和长正文场景仍有意义。旧约 0.55 ms 的估计也受 CPU 计数更正影响，不能继续引用为精确预算。
3. 把 BM25 批量与所需候选预算对齐，保留可见性/过滤淘汰后的续扫；既有批量试验有少量有序 ID 改变，仍须归因，不把质量均值相同等同于逐条等价。
4. 再看 HNSW 页面访问、BM25 直接传分数/排名、串行缓冲回放等结构优化；独立衡量收益和维护风险。
5. 持久 worker 是后续并行问题，不是这次串行 CPU 图的首因。并行模式尚需单独的生命周期/等待诊断。

向量普通执行器已采到 `cosine_distance` 25.66%、其中 TOAST 25.10%；首轮 Bypass 的 7,282 个样本未见这两条路径，支持路径差异，但其后测 P50 从约 1.57 ms 跳到 123 ms，且出现单线程 CPU 超过墙钟的计时异常，**该轮禁止用于时延/阶段 CPU 收益对比，异常原因尚未定位**。原始文件保留于 `验证/火焰图/D2_vector_bypass/`，汇总显式标记 `quality_warnings` 并禁用阶段 CPU 估计，不能选择性只报告前测的快值。

**Bypass 复核已正常完成：**7,488 样本，前/采样/后测 P50 为 1.591/1.612/1.693 ms；没有 cosine_distance 或 TOAST fetch 栈，而 pg_detoast_datum 的快速检查仍存在。500 条查询返回的全部有序 ID hash 与通用路径相同。旧阶段 CPU 毫秒估计已撤回，但调用栈仍支持它消除了候选输出冗余；不能据此声称图搜索本身大幅变快。**这是执行路径对照，不是 PLAIN 对照，也不代表 HybridRecall 已获得同样加速。**

与 Milvus 的差距归因仍有限：本轮没有采 Milvus 的服务端图；已完成的同期端到端比较见 §0.8。这里定位的是 openGauss 自身可优化成本，尚不能量化两系统每个内部阶段的差异。D1 火焰图、冷态、更大候选和新布局并发吞吐尚未验证。

#### 为什么建了两次 HNSW，以及后续复用方式

两次分别为两张新表建独立索引，各约 649/651 秒。HNSW 中保存的 heap TID 绑定所属表，不能将原表索引挂到新表。**普通 UPDATE 会自动维护索引，不是所有存储调整都必须手工 REINDEX**；本次新表建索引用于保留原基线和两种布局，避免覆盖已有结果。现有两张表与索引均可继续复用，不需要重复构建。

当前无需再围绕已消除的 TOAST 预报叠加收益。全 PLAIN 剩余用户 CPU 样本中 HNSW 约 49.5%、BM25 扫描约 22.0%、SQL 生命周期等约 14.8%。继续优化应针对这些剩余成本，且长正文场景仍需要 rank-only/正文布局等专门设计。线程计数修正后的新图及慢查询对照见下节。

### 0.9 P99、Bypass 与慢查询火焰图：下一步优化落点

#### P99 差额不是稳定的全面落后，但存在可复现的慢查询

复算 §0.8 保存的逐查询数组，整体 P99 为 OG 4.1319 vs MV 4.0322 ms，差 0.0997 ms。两轮分别为 **4.3028 vs 4.1085**、**3.8655 vs 3.9147**：胜负发生反转。按每个窗口内完整 500 查询循环进行 2000 次分层重采样，差额的 2.5%–97.5% 范围约为 −0.069 至 +0.284 ms。它只是对已有样本的敏感性检查，不是独立多轮实验、不是生产 SLA 置信区间，不能据此声称两系统已证明相等。

OG 的查询下标 153、135 在 46 次计时中位数为 4.206、4.083 ms，分别有 26、21 次进入整体最慢 1%；两个查询只占查询集 0.4%，却占 230 个尾部样本的 47 个（约 20.4%）。排除这两条后重算 P99 为 4.064 ms，但**不能删除困难查询后对外报告优化成绩**，其余尾部抖动也仍存在。

证据：[历史尾延迟脚本](验证/P99分析/分析历史尾延迟.py)、[逐查询统计与重采样结果](验证/P99分析/历史尾延迟归因.json)。

#### 不是没走索引，也不能只归因于没走 Bypass

融合计划明确为 `Hybrid Recall → Limit → BM25 Index Scan` 与 `Limit → Ann Index Scan`，两路实际各 100 行，Serial RRF 返回 Top-10。`enable_opfusion=on` 不等于整个 Hybrid Recall 会 Bypass：`getSelectFusionType()` 的 ANN 快路径要求顶层为 ANN 或 Limit→ANN，Hybrid Recall 不在其支持范围内。

针对同一张全 PLAIN 表，进行了 500 查询×4 轮、正反顺序、每块前两遍预热的只读支路对照。向量两档都是 `SELECT id ... ORDER BY embedding <=> $1 LIMIT 100`，只改会话 `enable_opfusion`；所有有序 ID 与已保存候选一致。附加 `/proc` 探针位于 execute/fetch 计时区间外，但会改变请求间隔，**这组不是新的 Milvus 同期基准，也不能把不同单路 P50 相加来拆融合时延**。

| 路径 | P50 ms | P99 ms |
|---|---:|---:|
| 完整融合 | 2.5152 | 4.2241 |
| 向量通用执行器，100 候选 | 1.6939 | 3.0348 |
| 向量 Bypass，100 候选 | 1.6693 | 3.1109 |
| 文本单路，100 候选 | 0.8922 | 1.6218 |

Bypass 其中一轮明显波动，不能只取有利轮次；本批合计既未证明大幅提速，也没有稳定改善 P99。慢查询 153 在两种向量路径中位数仍约 3.239/3.307 ms，135 约 3.149/3.075 ms。

更重要的是，[慢查询 Bypass 火焰图](验证/火焰图/D2_all_plain_slow153_135_Bypass/cpu.svg)实际捕获 `SelectForAnnFusion::execute`，留存样本中 HNSW 搜索占 **85.58%**，未采到 TOAST fetch 或 cosine 输出重算。**该组 record.log 报告丢失 3 个 chunk，占比只作定性参考，不用于精确阶段 CPU 比较。** 真实调用栈仍证实 Bypass 确实执行，结合无采样的同 SQL 对照，不能认为启用 Bypass 就消除了慢查询。脚本最初在预热前保存的 EXPLAIN 尚未进入 generic-plan 阶段，所以不显示 `[Bypass]`；不能用那个早期标签否定后续真实运行栈。

#### 从调用栈推导、已做对照的优化空间

1. **优先研究 HNSW 页访问成本。** 调用链为 `HnswSearchLayer → MmapLoadElement → HnswLoadElement → ReadBuffer → BufferAlloc → buf_hash_operate/PinBuffer`。实查 `enable_mmap=off`、`hnsw_use_mmap=off`，所以 `MmapLoadElement` 只是尝试后回到 buffer 路径，不能因函数名就说已 mmap。应先测同一请求内重复 block 的比例，再考虑有生命周期边界的页/节点复用或邻居批量访问；必须保留 pin/锁、VACUUM 可见性、更新失效和资源上限。仅见哈希函数宽并不能证明哈希碰撞或锁争用，不能盲目扩大 hash 表或绕过 buffer 管理。
2. **取参内联已做反证；完整的 HNSW 内置距离直调仍未做。** 慢查询图里的 `pg_detoast_datum` 和 `DatumGetFloat8` 是 HNSW 通用函数接口/快速检查，不是 TOAST fetch。仅把 `vector_negative_inner_product` 的两次普通 varlena 头检查内联后，前后图中 `pg_detoast_datum` self 由 4.159% 降到 0.028%，但调用者 self 由 0.088% 升到 4.102%；三次跨二进制切换没有可复现的端到端收益，最终已回退，见[方案 1 结论](验证/detoast内联对照/方案1最终结论.json)。下一候选若实施，必须是资格严格的内置 vector opclass 直调：一次性绕过 `FunctionCall2Coll/fmgr`、两次 Datum 取参、重复维度检查和结果 `DatumGetFloat8`；自定义函数、其他向量类型及 PQ/RabitQ/LSG 保留回退。不能再把函数帧占比机械当作可省净收益。
3. **向量核不是“没开 SIMD”。** 当前安装二进制的 `VectorInnerProduct` 已含 `vmulps/vaddps` 的 256-bit AVX 指令。应先减通用接口和访页成本，而非把循环改 SIMD 就承诺翻倍。多累加器/FMA 等若另做，须单独验证浮点变化引起的候选排序/召回差异。证据：[实际二进制反汇编](验证/P99分析/距离函数二进制核验.json)。
4. **续扫候选保存是次级点，已做反证。** `relaxed_order` 在搜索中保存 discarded 候选，关闭后不再保留这部分续扫状态。同一现有图、无过滤、500 查询、每档 10,000 次执行的四轮正反对照：P50 2.4878→2.4584 ms，P99 3.9726→3.8873 ms，user CPU 2.212→2.182 ms/请求，minor faults 79.50→67.71/请求，所有有序 Top-10 相同、recall=0.883。**仅约 1%–2% 收益，且最慢两条未一致改善，不是主要突破口。** 新[关闭续扫火焰图](验证/火焰图/D2_all_plain_slow153_135_no_resume/cpu.svg)仍有 HNSW 66.49%、HNSW 内 BufferAlloc 22.83%、内积 14.01%，主热点没有消失。不能全局关闭：过滤/MVCC 淘汰后可能需要续扫补足候选。证据：[对照脚本](验证/P99分析/融合续扫开关对照.py)、[汇总](验证/P99分析/融合续扫四轮/summary.json)。第一块预热附近同时进行过旧 perf 文件离线解码；保留全部轮次，不把小幅变化当稳健生产收益。

方案 1 实验期间改过并多次编译产品代码，但现已完整回退；最终 `vector.cpp` 对 Git 基线零差异、安装二进制恢复原 SHA。全程未重建索引、未改变持久配置，Milvus 保持停止；这些测试不能与旧 Milvus 数字拼成“又反超”的同期成绩。若继续实现完整 HNSW 距离直调，仍须按同索引、全查询、真实过滤/更新正确性和前后火焰图验证；页访问复用的维护风险更大，不能跳过设计。

#### 测量更正与采样质量

实查同一新线程 `/proc/TID/stat` 会返回进程累计的 CPU/缺页，而 `/proc/TGID/task/TID/stat` 返回该线程计数。Linux 6.18 的 [proc 路由](https://github.com/torvalds/linux/blob/v6.18/fs/proc/base.c) 与 [do_task_stat 的 whole 分支](https://github.com/torvalds/linux/blob/v6.18/fs/proc/array.c)也区分进程组与线程。因此旧“主线程 CPU 降 20%”、旧阶段毫秒和超墙钟 CPU 的解释均不能继续使用。原始文件保留，汇总器已对旧 scope 写入 warning 并将阶段估计置 null。

新脚本按 task 路径读取 CPU；逐请求诊断用 `schedstat` 的纳秒 runtime（用户+内核），但本机 `sched_schedstats=0`，runqueue=0 不能作为无调度等待的证据。完整查询集测试在 500-query 循环边界结束，保证查询权重一致。

`D2_all_plain_full_CPU修正` 和 `_低扰动` 的 64-page perf 环分别丢失 1/2 个 chunk；第一组采样期 mean 还明显高于前后无采样段，均只保留为定性参考，不用于阶段毫秒。后续 `_扩环` 将采样器自身环增至 256 页、199 Hz，在现有锁页额度内成功完成且无丢失，不涉及数据库 shared_buffers、索引或内核配置修改。慢查询/Bypass/关闭续扫各图同样保留前后无采样段；图的采样占比不是 P99 占比。

原表追加的 `D2_external_full_CPU修正_扩环` 无丢失，但前/后无采样 mean 为 5.460/3.521 ms，切布局后仍明显漂移；同样禁用阶段毫秒，不拿它与全 PLAIN 的独立图恢复“CPU 降约 20%”。汇总器新增前后无采样 mean 相差超过 15% 的保守提示；它是质量筛查规则，不是统计显著性检验。Bypass 图的丢失警告也已写回派生 JSON，原始数据未删除。

## 2. 五个量化结论

### 2.1 融合本身零开销——之前"~1.8ms 融合开销"是推算错误

Fusion Time 全档 0.006~0.024ms。串行 fusion total ≈ text + vec 严格相加（6.16 ≈ 1.50+4.17）。
之前报告用客户端口径推算的"融合+算子开销 1.8ms"实为：**支路在融合内取 100 行（含 payload 契约）比单路直查取 10 行慢的部分**（text 0.54→1.50、vec 2.70→4.17@ef400），不是融合算子的成本。

### 2.2 延迟大头是向量支路：质量对齐档占 68%，大候选档占 83%

- ef=400 时 vec 支路 4.17ms / total 6.16ms；
- cand=1000 时 vec 支路 18.93ms / total 22.69ms；
- **ef 的延迟杠杆实测**：ef 400→100，vec 支路 4.17→2.20ms（-47%），代价是 recall@100 1.00→0.80。
  → 若 OPT-3（HNSW 同质量所需 ef 从 4x 降到 1x）落地，质量对齐档 total 6.16→**~3.7ms（-40%）**，是单项收益最大的优化，比支路重叠（上限 min(text,vec)=1.5ms）杠杆更高。

### 2.3 并行（force）的重叠收益被固定开销吃掉

force cand=100：vec 支路墙钟 4.17→2.39ms、overlap 1.22ms（两支路真并发），**但 total 6.59 ≈ 串行 6.16——重叠省下的 ~1.8ms 被 worker 启动 + stream 传输抵消**。
（另注：force 的 worker 因 OPT-1 缺陷实际用 ef=40，其 vec 2.39ms 的质量是缺陷态，修复后该数字会回升。）
→ OPT-2 档2 的"线程内交替消费"（无 worker/stream 开销）才是拿回 min(text,vec)=1.5ms 的路径；worker 并行只在支路更重（cand=1000）时有净收益空间，但当前也被抵消（24.0 vs 22.7）。

### 2.4 文本支路稳定且便宜

text 支路 1.3~1.5ms（cand=100）/3.6ms（cand=1000），随候选数近线性、不受 ef 影响。BM25 是 OG 的结构性强项（单路直查 0.54ms vs Milvus 2.3ms）。

### 2.5 与 Milvus 的延迟模型对比（客户端口径）

| 构成 | openGauss（off, ef400） | Milvus（ef100） |
|---|---|---|
| 文本路 | 1.50 ms（服务端） | ~2.3 ms（客户端单路） |
| 向量路 | 4.17 ms（服务端，ef400） | ~2.4 ms（客户端单路） |
| 融合 | 0.006 ms | 含在返回中 |
| 执行模型 | text + vec **串行相加** | 两路**并发取 max** |
| 端到端 P50 | 5.0 ms | 2.7 ms |

Milvus 无 per-stage 分解接口，其单路数字取自客户端单路基准（含 gRPC 往返），与 OG 服务端分解不可直接相减——上表只作结构对照。
**差距 ≈ 串行相加 vs 并发取 max 的执行模型差 + ef 效率差（4x ef 才达同 recall）**，融合算法本身两边都可忽略。

## 3. 缓存与并发维度（摘自报告，分析视角）

1. **冷热敏感（OG 特有）**：交替负载 P50 冷 32ms→热 11ms→独占 5ms。HNSW 索引 410MB > shared_buffers，驱逐后重读 dominates。Milvus 常驻内存无此效应。EXPLAIN 分解在热态采得；冷态下 vec 支路占比会更高（页读入都在向量路）。
2. **并发扩展（OG 的结构性优势）**：1→8 并发 OG off 4.7x（883 QPS）vs Milvus 2.8x（977 QPS）。原因：OG 单查询串行算子少占核，多连接并行度好；Milvus 单查询内部已并发，多连接边际收益低。force 模式多连接下反而 3.1x（双 worker/查询 × 8 连接 = 16 worker 挤 20 核 + stream 调度开销）。
