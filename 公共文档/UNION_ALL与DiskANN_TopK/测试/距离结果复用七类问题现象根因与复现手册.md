# 距离结果复用七类问题：现象、根因与复现手册

## 1. 用途与范围

本文交给迁移后的模型独立分析和复现，范围只包括 ANN/DiskANN **距离结果复用及其直接依赖的合并行身份、距离尺度和输出顺序**。本文不收录 UNION ALL 必需列裁剪问题，也不收录测试注释或 golden 不同步等纯测试维护问题。

源端最终修复基线为：

```text
仓库：/home/qiumc/data/code/cpp/openGauss-server
分支：integration/multimodal-stacked
提交：84f0a21f543da7ffaa9582d44d0ff0772068c9ae
```

本文选取 7 个问题：`K1～K5、R1、R2`。源端均曾真实复现，最终基线已经修复。迁移后的实现不应照搬源端结论，应重新确认目标索引是否存在相同机制，再执行对应用例。

未计入本文的 `R3` 是 immediate delete 的事务回滚与旧快照可见性问题；它在 `ann_orderby_distance_reuse=off` 时同样发生，归入 DiskANN 删除协议，而不作为本次“距离复用问题”示例。完整历史仍见[ANN 距离复用缺陷修复与验证报告](ANN距离复用缺陷修复与验证报告.md)。

## 2. 先统一复现判定口径

### 2.1 不要只看命令退出码

这些问题大多是静默错值、漏行、重行或顺序错误。`gsql` 返回 0 只说明 SQL 执行完成，不说明结果正确。每个用例都必须检查明确的数值、行数或单调性断言。

### 2.2 必须证明查询真正命中复用

复现时至少保存：

1. `EXPLAIN (VERBOSE, COSTS OFF)`；
2. 当前距离复用 GUC；
3. 实际索引访问路径；
4. 复用值与独立参考值；
5. 行 ID、TID 或目标索引的等价稳定身份。

把被测 SELECT 直接包进 CTAS、聚合或修改节点，可能改变消费者链，使优化器拒绝复用。此时结果虽然正确，却没有覆盖被测路径。归档用例通过动态执行独立 SELECT 后再保存结果，迁移时应保留这一形状。

### 2.3 源端运行入口

```bash
REPO=/home/qiumc/data/code/cpp/openGauss-server
INSTALL=$REPO/mppdb_temp_install
GCCLIB=/home/qiumc/data/code/cpp/binarylibs/buildtools/gcc10.3/gcc/lib64

env GAUSSHOME="$INSTALL" SSL_LIB_PATH="$INSTALL/lib" \
  LD_LIBRARY_PATH="$INSTALL/lib:$GCCLIB" \
  make -C "$REPO/src/test/regress" ann_orderby_distance_reuse_check
```

完整原生回归包含：

- `ann_orderby_distance_reuse`
- `ann_orderby_distance_reuse_safety`
- `ann_orderby_distance_reuse_lifecycle`

源最终基线的历史结果为 3/3 通过。迁移仓应使用自己的安装目录和测试入口，不应直接把源端通过记录当成目标端证据。

## 3. 七类问题总表

| 编号 | 问题现象 | 主要根因 | 核心判定 |
|---|---|---|---|
| K1 | 合并节点中的某些行得到其他行的 L2 距离 | 用节点代表向量的距离覆盖同节点全部 heap TID | 每行复用值必须属于当前可见行 |
| K2 | 近似 Cosine 改变外层 WHERE、比较和 InitPlan 的真假 | 只防护部分计划节点，遗漏普通表达式消费者和参数通路 | 近似值只能进入允许的排序/投影消费者 |
| K3 | 带归一化支持函数的“L2” opclass 返回错误尺度 | 只检查 support-1，忽略 support-2 已改变存储向量和距离语义 | 算子、opclass、AM 转换公式必须完全一致 |
| K4 | 相同向量超过合并桶容量后丢行；初步修复后又重行 | “桶满”被当成合并成功；扫描按节点而非逻辑行身份去重 | 容量溢出后不丢行、不重复 TID |
| K5 | 删除合并节点的代表行后，同节点其他存活行全部消失 | 代表 TID 被误当成整个共享节点的生命周期 | 删除一个成员不能删除仍有成员的节点 |
| R1 | heap TID 回收后，新行取得旧向量的距离 | 物理 TID 没有行代际；VACUUM 未清旧 owner，身份校验仍误认 | 必须真实触发 TID 再利用并核对新行距离 |
| R2 | 每行距离都算对，但输出出现 `1、0、2、1` 的逆序 | 先按代表向量排序，再逐行修正距离，却没有按最终值重排 | 候选必须按最终发布值单调有序 |

## 4. K1：合并节点把代表向量距离错误复用给其他行

### 问题现象

DiskANN 会按距离阈值把多个 heap TID 合并到一个图节点。阈值相等或接近不等于向量逐字节相等。修复前，节点距离被复制给同节点全部 TID，导致返回行的 `embedding <-> query` 与直接从 heap 计算的 `l2_distance()` 不一致。

源端固定数据中：

- 递归表达式执行器返回 9 行，其中 3 行距离错误；
- 融合表达式执行器返回 9 行，其中 5 行距离错误；
- HOT 更新后仍有 3 行错误。

### 问题根因

候选距离属于“索引节点代表向量”，执行器却把它当作“当前可见 heap 行”的值。扫描 epoch、row token 只能证明值来自本轮扫描，不能证明值属于节点内当前这个 TID。旧实现没有在发布距离时绑定候选身份、也没有对非 owner TID 做安全处理。

### 复现用例

权威用例位于：

- [安全回归 SQL](../../../src/test/regress/sql/ann_orderby_distance_reuse_safety.sql)，检索 `ann_merged_l2_t`；
- [修复前输出](ANN距离复用修复证据/安全回归_修复前.out)；
- [修复后输出](ANN距离复用修复证据/安全回归_修复后.out)。

核心夹具包含两组风险向量：

```sql
INSERT INTO ann_merged_l2_t VALUES
    (1, 'a', '[10000,20000,30000,40000]'),
    (2, 'b', '[10001,20000,30000,40000]'),
    (3, 'c', '[10002,20000,30000,40000]'),
    (4, 'd', '[10000,20001,30000,40000]'),
    (6, 'f', '[10,20,30,40]'),
    (7, 'g', '[10.00001,20,30,40]'),
    (8, 'h', '[10.00002,20,30,40]'),
    (9, 'i', '[10,20.00001,30,40]');
```

对同一行同时输出复用距离和独立 heap 距离，并用 `float8send()` 比较。修复或正确迁移后的判定是：返回 9 行，递归、融合和 HOT 三组 mismatch 都为 0。不能只检查行数。

## 5. K2：近似距离进入语义消费者后改变 SQL 真假

### 问题现象

Cosine 的 AM 转换值与精确 SQL 值存在允许的近似误差。该值用于排序可以符合既定契约，但若继续进入外层 WHERE、布尔比较或 InitPlan，就会改变查询语义。

固定用例中，精确值约为：

```text
0.00008162265858591145
```

近似复用值约为：

```text
0.00008159875869750977
```

阈值取 `0.00008161`。修复前 `off` 返回 0 行，`cosine` 返回 1 行；普通比较和 InitPlan 也会由 false 变成 true。

### 问题根因

旧规划器通过枚举 Join、Agg 等“不安全节点”决定是否允许复用，遗漏了：

- 普通上层 Filter；
- 计算投影中的比较表达式；
- `PARAM_EXEC`/InitPlan 的值传递；
- UNION ALL 兄弟分支上下文恢复。

这种黑名单无法覆盖所有消费者。正确做法是沿距离列消费链只允许经过验证的透明传递，其余语义消费者拒绝近似复用。

### 复现用例

权威用例位于[安全回归 SQL](../../../src/test/regress/sql/ann_orderby_distance_reuse_safety.sql)，检索 `ann_threshold_t`：

```sql
SELECT id, distance FROM (
    SELECT /*+ indexscan(ann_threshold_t ann_threshold_cos_idx) */
           id, embedding <=> '[11,23,35,47]'::vector AS distance
    FROM ann_threshold_t ORDER BY distance LIMIT 10
) s
WHERE distance < 0.00008161::float8;
```

还必须执行同文件中的 computed projection 和 InitPlan 两种形状。正确迁移后的判定是：

- 外层 WHERE 返回 0 行；
- `distance < threshold` 为 false；
- InitPlan 比较为 false；
- EXPLAIN 表明这些形状没有错误地把近似引用送入语义消费者。

## 6. K3：自定义 L2 opclass 实际改变了距离尺度

### 问题现象

自定义 opclass 同时声明 L2 support-1 和 `vector_norm` support-2。SQL 表面仍使用 `<->`，但索引内已对向量归一化，AM 距离与原始向量 SQL L2 不在同一尺度。

固定 4 行用例中，`off` 的 SQL 距离为：

```text
5
6.70820393249937
8.06225774829855
10
```

修复前开启 L2 复用后得到：

```text
0
0.632455536745837
0.894427197663918
2
```

### 问题根因

优化器、执行器和 AM 只看到 support-1 是 L2，就假定内部值可按普通 L2 转换，没有检查 support-2 已改变索引存储和距离语义。这不是少做一次或多做一次 `sqrt`，而是输入向量本身已经变化。

### 复现用例

权威用例位于[主回归 SQL](../../../src/test/regress/sql/ann_orderby_distance_reuse.sql)，检索 `normalized_l2_ops` 和 `ann_normalized_l2_t`。

```sql
CREATE OPERATOR CLASS normalized_l2_ops
FOR TYPE pg_catalog.vector USING diskann AS
    OPERATOR 1 pg_catalog.<->(pg_catalog.vector, pg_catalog.vector)
        FOR ORDER BY pg_catalog.float_ops,
    FUNCTION 1 pg_catalog.vector_l2_squared_distance(
        pg_catalog.vector, pg_catalog.vector),
    FUNCTION 2 pg_catalog.vector_norm(pg_catalog.vector);
```

正确迁移后的判定是 `normalized_l2_reuse_mismatches = 0`，并且计划没有把不满足目标语义契约的 AM 值伪装成普通 SQL L2。目标索引若有自己的公式，应按目标公式建立同类“不一致 opclass/配置”反向用例，不能机械照搬“存在 norm proc 就拒绝”。

## 7. K4：合并桶容量溢出导致丢行或重行

### 问题现象

源 DiskANN 旧格式每个节点最多保存 `DISKANN_HEAPTIDS=10` 个 heap TID。插入 12 行完全相同的向量后：

- 最初缺陷版本只返回 id 1～10，静默丢失 2 行；
- 第一版补救保留溢出节点后返回 13 行，其中 id 12 出现两次。

在线再插入 id 13、14 时还会经过 GenericXLog 路径，可能出现相同的丢行、重行或未完成 WAL 状态。

### 问题根因

问题由三层机制叠加：

1. `AddDuplicateNeighbor` 容量满时失败，上层却把它当成合并成功，不再为当前行链接新节点；
2. 保留溢出节点后，旧 frozen point 和新节点可能同时保存同一 heap TID；
3. 扫描按“节点 + TID”去重，而 SQL 逻辑行身份只有 heap TID，所以同一行跨节点仍会重复。

此外，多页候选合并若持有当前页锁再申请候选页锁，会形成反向锁序风险。

### 复现用例

权威用例位于[主回归 SQL](../../../src/test/regress/sql/ann_orderby_distance_reuse.sql)，检索 `ann_duplicate_capacity_t`。

```sql
INSERT INTO ann_duplicate_capacity_t
SELECT g, '[10,20,30,40]'::vector
FROM generate_series(1,12) g;
```

正确迁移后的判定：

- 建索引后 heap、`off`、`l2` 都返回 12 个不同 id；
- 在线插入 id 13、14 后三者都返回 14 个不同 id；
- off/on 的重复敏感差分为 0；
- 如果目标索引没有共享 TID 桶，应写明“不适用”的结构证据，并验证目标自己的容量和去重边界。

## 8. K5：删除代表 TID 误删整个共享节点

### 问题现象

两组向量各有 6 行，并共享各自的 DiskANN 节点。对每组删除索引当前首先返回的一行后，heap 中两组都剩 5 行。修复前，其中一组仍能返回 5 行，另一组通过索引返回 0 行。

随机 frozen point 可能使消失的是 A 组或 B 组，因此复现断言不能硬编码“必须丢 B 组”；应断言任一组的 heap/index 计数不一致。

### 问题根因

旧删除路径先比较 IndexTuple 自身的代表 TID。只要删除目标等于代表 TID，就直接断边并把整个节点标死，没有先检查共享 `heaptids[]` 中是否还有存活成员。代表地址是存储实现细节，不代表共享节点已无逻辑行。

### 复现用例

权威用例位于[主回归 SQL](../../../src/test/regress/sql/ann_orderby_distance_reuse.sql)，检索 `ann_merged_delete_t`。

用例分别查询 A/B 组当前首个 id，删除这两个 id，再对 heap 和强制 DiskANN 查询分别计数。正确迁移后的判定为：

```text
heap_a = 5
heap_b = 5
index_a = 5
index_b = 5
```

目标索引没有“多个逻辑行共享一个物理候选”机制时，该问题可判定为不适用；判定依据必须是目标数据结构和删除路径，不能只凭测试未触发。

## 9. R1：heap TID 回收后复用了旧行距离

### 问题现象

旧行 id=1、向量 `[10,20,30,40]` 位于 `ctid=(0,1)`。删除、VACUUM 并真正回收该槽位后，新行 id=2、向量 `[100,200,300,400]` 再次取得同一 `ctid=(0,1)`。

查询向量仍为 `[10,20,30,40]`。修复前结果是：

| 模式 | 返回 id | 复用投影值 | 新行独立 heap 距离 |
|---|---:|---:|---:|
| off | 2 | 492.95030175465 | 492.95030175465 |
| l2，递归表达式 | 2 | 0 | 492.95030175465 |
| l2，融合表达式 | 2 | 0 | 492.95030175465 |

### 问题根因

物理 TID 不携带行代际。旧实现的 VACUUM 回调没有清理死 TID 和失效的向量 owner；后续又仅用 `vectorTid == heapTid` 判断当前行可直接复用。槽位重新分配后，数值相同的 TID 已代表另一条逻辑行，但旧索引向量和旧距离仍被认作当前值。

扫描 epoch 和 row token 也无法单独解决这个问题，因为它们证明的是“本轮发布”，不是“索引向量与当前 heap 行属于同一代”。

### 复现用例

- [完整 SQL](ANN距离复用复审证据/03_tid_recycle.sql)
- [修复前实际输出](ANN距离复用复审证据/03_tid_recycle.out)
- [修复后生命周期输出](ANN距离复用生命周期修复证据/生命周期_修复后.out)

运行：

```bash

CASE=/home/qiumc/data/code/cpp/公共文档/UNION_ALL与DiskANN_TopK/测试/ANN距离复用复审证据/03_tid_recycle.sql
env LD_LIBRARY_PATH="$INSTALL/lib" "$INSTALL/bin/gsql" \
  -X -h /tmp -p 55440 -d postgres -f "$CASE"
```

两个 `pg_sleep(6)` 是为了跨过源实例 5 秒的延迟清理周期。迁移环境必须按自己的回收协议调整。只有输出明确证明新旧 ctid 相同，才算触发了本用例；没有发生 TID 再利用只能记为“未触发”。正确迁移后的新行距离应为 `492.95030175465`，两套表达式引擎都不能返回 0。

## 10. R2：逐行值正确，但候选仍按旧代表值逆序输出

### 问题现象

K1 的第一轮修复对非代表 TID 按 heap 向量重新计算了正确距离，但没有恢复排序。固定 9 行用例的前四个 `(id, distance)` 为：

```text
(2, 1), (1, 0), (3, 2), (4, 1)
```

所有行的投影距离都与独立 heap 距离一致，`incorrect_values=0`，但存在两个相邻逆序对。修复前 `off` 和 `l2` 都能出现逆序。

### 问题根因

底层先按节点代表向量距离排序，再按节点内 `heaptids[]` 顺序展开。逐行 heap recheck 只修改每行最终值，没有按这些最终值重新排序；同时 AM 声称 `xs_recheckorderby=false`，上层 Limit 或 Merge Append 会信任这个错误顺序。

因此“每行距离正确”和“按该距离有序”是两个独立条件。只修正投影值仍可能让分支 LIMIT 提前截断正确候选。

### 复现用例

- [完整 SQL](ANN距离复用复审证据/01_merged_order.sql)
- [修复前实际输出](ANN距离复用复审证据/01_merged_order.out)
- [最终生命周期回归 SQL](../../../src/test/regress/sql/ann_orderby_distance_reuse_lifecycle.sql)

运行：

```bash

CASE=/home/qiumc/data/code/cpp/公共文档/UNION_ALL与DiskANN_TopK/测试/ANN距离复用复审证据/01_merged_order.sql
env LD_LIBRARY_PATH="$INSTALL/lib" "$INSTALL/bin/gsql" \

```

正确迁移后的判定是：

```text

incorrect_values = 0
```

还要在真实 `LIMIT` 和联合分支 Top-K 上验证最终顺序。把结果按 id 重新排序后再比较、只比较结果集合，都会掩盖该问题。

## 11. 交给迁移后模型的执行清单

迁移后的模型应逐项输出以下记录：

| 项目 | 必须记录的内容 |
|---|---|
| 环境 | 目标仓路径、分支、commit、实际运行二进制、`version()`、构建类型 |
| 适用性 | K1～K5、R1、R2 在目标索引上的对应数据结构和调用路径；不适用项给代码依据 |
| 计划 | 每个用例的 EXPLAIN，证明命中目标索引及复用/拒绝路径 |
| 结果 | 复用值、独立参考值、行数、distinct 行数、逆序数和 TID/版本证据 |
| 判定 | 已复现、未复现、未触发、不适用或已通过；不得把“未触发”写成“没有问题” |
| 修复 | 若发现问题，记录修改文件、根因、修复前后对照和新增回归 |

最后至少运行目标仓的原生回归入口。正向用例必须证明距离确实来自 AM 复用通道；反向用例必须证明不安全形状被拒绝。全部回退到原 SQL 表达式虽然可能结果正确，但不能算距离复用迁移通过。
