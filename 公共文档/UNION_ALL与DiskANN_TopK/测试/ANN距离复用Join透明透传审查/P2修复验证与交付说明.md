## 2. 现象与根因

旧逻辑允许 `T_HashJoin`，但不允许右侧的 `T_Hash`。计划 walker 进入 Hash 时把 `approximatePlanSafe` 置为 false，即使父 Join 只按整数 id 匹配。扫描因此保留精确距离表达式，漏掉本来安全的复用。

同一 8 行向量基线，旧版本 ANN 位于探测侧时有 1 个 AM 引用扫描、8 行输出区别于原 SQL 精算值；位于构建侧时没有 AM 引用、全部仍为精算值。典型 UNION ALL 的 delta 分支复用，snapshot 的 Hash 构建侧不复用。两种情况均是漏优化，不是行集错误。

修复在 `ann_orderby_node_allows_approx()` 加入 `T_Hash`，检查只有一个左输入，并继续执行公共空 qual/透明 targetlist 检查。父 HashJoin 的距离消费者检查继续决定安全性，Hash 不得把已为 false 的上下文恢复为 true。

## 3. 物化、溢写与重扫依据

源仓 Hash 的键表达式由父 HashJoin 保存并初始化；普通 Hash 只物化子节点的完整 tuple。`ExecHashTableInsert()` 取得 `MinimalTuple` 后复制全部字段，距离值已经是其中的标量。分批通过 `ExecHashJoinSaveTuple()` / `ExecHashJoinGetSavedTuple()` 保存、恢复 tuple。Hash 匹配时不会从 ANN 扫描状态中重新读取上一行的距离。

本次无需增加执行器字段或补丁。目标同源仓若改变了 Hash 键归属、物化协议或新增过滤表达式，必须按迁移指南重新核对。

## 4. 测试结果

### 4.1 原问题的前后对照

16 类边界 SQL × 两种表达式引擎 × 关闭/开启复用，合计 64 次查询执行，附对应 EXPLAIN。32 组对照的 ID 多重集、NULL 数量均保持一致。

| 场景 | P2 前 AM 引用扫描数 | P2 后 AM 引用扫描数 | 修复后结果 |
|---|---:|---:|---|
| 普通 Hash 的 ANN 构建侧 | 0 | 1 | 全部 8 个 ID 相同，8 行实际使用近似值 |
| 普通 Hash 的 ANN 探测侧 | 1 | 1 | 全部 8 个 ID 相同 |
| 典型 UNION ALL + Hash Right Anti Join | 1 | 2 | delta/snapshot 均复用，全部 6 个保留 ID 相同 |
| P1 整行 Nested Loop/Merge/LATERAL 负向 | 0 | 0 | 保留 id=1，仍使用精确 SQL 值 |

证据：[P2修复前_边界验证.out](P2修复前_边界验证.out)、[P2修复后_边界验证.out](P2修复后_边界验证.out)。原脚本 [复现与边界验证.sql](复现与边界验证.sql) 可重新执行；历史标签 `BUG_...` 保留以追踪旧问题，当前结果已通过。

### 4.3 分批与重建

仅 32 行四维向量，附每行 4kB PLAIN payload。保留 payload 为查询输出以防优化器裁剪掉它。分别在 L2/Cosine × 两种表达式引擎下运行，12 个场景均通过：

| 场景 | work_mem | 返回行数 | 实际 Hash 分批 | 实际 Hash 多次执行 | 距离/payload 与同模式直接扫描一致 |
|---|---|---:|---|---|---|
| 内存驻留 | 4MB | 32 | 否 | 否 | 是 |
| 分批溢写 | 64kB | 32 | 是 | 否 | 是 |
| LATERAL 参数改变，重新构建 | 64kB | 93（32+31+30） | 是 | 是 | 是 |

测试解析实际 `EXPLAIN ANALYZE` 的 Batches 和 Hash loops；低内存设置本身不算溢写证据。它同时检查 off/on 的 ID 多重集、预期行数，以及复用输出与独立 ANN 复用扫描之间的逐位距离和完整 payload 一致性。近似 Cosine 的数值基线是相同 AM 公式，而不是原 SQL 精算值。
