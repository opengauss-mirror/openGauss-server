## 3. J1：整行记录中的距离绕过了消费检查

### 3.1 问题位置

关键代码在 [planner.cpp:886](../../../../src/gausskernel/optimizer/plan/planner.cpp:886)：

```cpp
if ((IsA(node, Var) || IsA(node, Param)) && exprType(node) == FLOAT8OID) {
    return true;
}
```

`ann_orderby_join_expr_consumes_distance()` 还检查直接出现的 L2/Cosine 操作符及 `AnnOrderByRef`，但这些检查没有覆盖“一个 RECORD 值内部包含 distance”。

### 3.2 最小触发 SQL

完整建表、8 行数据、建索引和开关对照见 [最小复现.sql](最小复现.sql)。核心查询为：

```sql
SELECT q.id, q.distance
FROM
(
    SELECT id, embedding <=> '[11,23,35,47]'::vector AS distance
    FROM vectors
    ORDER BY embedding <=> '[11,23,35,47]'::vector
    LIMIT 40
) q
JOIN gates g
  ON q = ROW(g.id, cosine_distance(
      '[2,5,8,11]'::vector, '[11,23,35,47]'::vector))
ORDER BY q.distance;
```

这里 `q` 不是“只比较 id”，而是整行 `(id, distance)`。右侧距离由常量向量精确计算；id=1 对应向量恰好为 `[2,5,8,11]`。

### 3.3 真实结果

关闭复用：

```text
 id |      distance
----+---------------------
  1 | .000927228781839928
(1 row)
```

开启 `ann_orderby_distance_reuse=cosine`：

```text
 id | distance
----+----------
(0 rows)
```

没有 Join 的基线中，id=1 在两种模式下都能被索引召回：

| 模式 | id | distance |
|---|---:|---:|
| off | 1 | 0.000927228781839928 |
| cosine | 1 | 0.000927209854125977 |

距离数值的细小差异本身符合近似约定。但是 `record_eq` 会比较记录内的距离字段，导致精确比较本应匹配的这一行被丢弃。这违反了“Join 只透传、不消费近似距离”的约束。

### 3.4 问题计划

开启复用后的实际 Nested Loop 计划形态为：

```text
Nested Loop
  Output: q.id, q.distance
  Join Filter: (q.* = ROW(g.id, .000927228781839928::double precision))
  -> Subquery Scan on q
       Output: q.id, q.distance, q.*
       -> Limit
            Output: vectors.id, ((vectors.embedding <=> '[11,23,35,47]'::vector))
            -> Ann Index Scan using vectors_cos
                 Output: vectors.id, ((vectors.embedding <=> '[11,23,35,47]'::vector))
                 Order By: (vectors.embedding <=> '[11,23,35,47]'::vector)
  -> Materialize
       Output: g.id
       -> Seq Scan on gates g
            Output: g.id
```

完整原始输出保存在 [最小复现实测.out](最小复现实测.out)，没有通过手改内核或伪造计划模拟这个错误。

### 3.5 根因链

1. `setrefs` 后，Join 条件里读取的是 `q.*` 这个 RECORD 引用，不是一个显式的 FLOAT8 距离 Var。
2. 右侧距离表达式是常量，可以被折叠成 FLOAT8 Const；Const 不属于当前禁止条件。
3. `expression_tree_walker()` 把 Var/Param 当叶子节点，不会穿过一个 RECORD Var 自动追踪其各字段的生产来源。相关代码见 [nodeFuncs.cpp:1793](../../../../src/common/backend/nodes/nodeFuncs.cpp:1793)。
4. Join 条件因此被误判为“不消费距离”。
5. `SubqueryScan.targetlist` 中的整行 Var 又满足现有“只要是 Var/Const 就透明”的检查。
6. 安全标记一路保持 true，扫描的精确距离投影被替换成 `AnnOrderByRef`。
7. 记录中的 distance 随之变为近似值，影响 Join 成员资格。

所以问题不在 AM 的 Cosine 转换公式，也不在 EXPLAIN 双括号展示；是优化器的依赖判断不完整。

### 3.6 已复现的三个入口

| 主矩阵编号 | 入口 | off / cosine 返回行数 | 漏判位置 |
|---|---|---|---|
| 8 | Nested Loop 的 `Join Filter: q.* = ROW(...)` | 1 / 0 | `joinqual` 中的 RECORD Var |
| 9 | Merge Join 的 `Merge Cond: q.* = ROW(...)` | 1 / 0 | `mergeclauses` 中的 RECORD Var |
| 10 | LATERAL 内部扫描使用外层 `q.*` | 1 / 0 | `nestParams.paramval` 传入整行，而不是 FLOAT8 |

三者在 `enable_expr_fusion=off` 和 `on` 两种设置下均复现。

LATERAL 的危险性尤其容易遗漏：外层 NestLoop 自己可以没有 Join Filter，距离在内侧扫描过滤条件中被消费。只检查 Join 条件，不检查参数来源及其包含关系是不够的。当前已经检查了 `nestParams`，但复用了同一个不完整的类型判断，因此仍被绕过。

### 3.7 修复建议与验收

优先做保守正确的修复：Join 语义表达式及 NestLoop 参数遇到无法证明独立的整行/RECORD/复合类型引用时，禁止该子树近似复用。不能仅增加 `varattno == 0`：经过 setrefs 后，整行值也可以被放入一个普通输出槽位后再引用。

若以后希望对这类复杂计划也保持高覆盖率，应追踪“被改写的 target entry → 各层槽位 → 整行/复合值 → 条件及参数消费者”的真实依赖，不能仅凭返回类型猜测。

修复至少需要满足：

- 案例 8、9、10 在 cosine 模式仍返回 id=1，底层扫描不能错误出现可复用引用。
- 原有直接 FLOAT8 条件、显式类型转换、FLOAT8 NestLoop 参数三类负向测试继续正确禁用。
- 只用整数 id 匹配的 Join 仍可复用，不应把所有 Join 一刀切关闭作为最终修复。
- 复合类型、字段取值、整行传参的检查应覆盖全部 Join 条件字段，而非只补某一种 Join。

## 4. J2：Hash 构建侧被 Hash 节点错误阻断

### 4.1 问题位置

`ann_orderby_node_allows_approx()` 放行了 `T_HashJoin`，却没有放行 `T_Hash`；后者进入默认 false。见 [planner.cpp:972](../../../../src/gausskernel/optimizer/plan/planner.cpp:972)。

计划 walker 确实会下探 Hash 的子树，见 [planmem_walker.cpp:490](../../../../src/gausskernel/optimizer/util/planmem_walker.cpp:490)。因此并非 Hash 未被遍历，而是遍历时把 `approximatePlanSafe` 设为了 false。

### 4.2 普通 Hash Join 对照

相同 8 个向量，只交换实际 Hash Join 的构建侧/探测侧；连接条件始终仅为 `q.id = g.id`：

| ANN 所在侧 | 返回 ID 是否一致 | AM 引用扫描数 | 与原始精确距离位级不同的输出数 |
|---|---|---:|---:|
| 探测侧 | 是，8 行 | 1 | 8 |
| 构建侧，经过 Hash | 是，8 行 | 0 | 0 |

这里位级差异用 `float8send()` 比较，不靠显示小数位或双括号单独推断。构建侧的安全情况仍然重新求原始距离，属于漏优化，不是结果错误。

### 4.3 典型 snapshot/delete 场景也会触发

主矩阵案例 16 同时打开 UNION ALL Top-K 下推、列裁剪及 Cosine 距离复用。实际得到的局部计划为：

```text
Hash Right Anti Join
  Output: s.id, ((s.embedding <=> '[11,23,35,47]'::vector))
  Hash Cond: (d.id = s.id)
  -> Seq Scan on delete_t d
       Output: d.id
  -> Hash
       Output: s.id, ((s.embedding <=> '[11,23,35,47]'::vector))
       -> Ann Index Scan using snapshot_cos on snapshot_t s
            Output: s.id, (s.embedding <=> '[11,23,35,47]'::vector)
            Order By: (s.embedding <=> '[11,23,35,47]'::vector)
            Filter Mode: Post-Filter
            Filter: (s.id > 0)
```

snapshot 的距离完全没有被连接条件消费，仍然不能复用。delta 分支可以复用，所以两个 ANN 扫描只改写了一个。

相同视图选择 Merge Anti Join 时，delta、snapshot 两个扫描均可复用。两种 Join 计划在测试数据上均返回相同 6 个 ID；区别在于是否实现了预期复用能力。

### 4.4 修复建议与验收

在父 HashJoin 已通过完整距离依赖检查的前提下，允许满足透明输出约束的 Hash 把安全上下文传给其构建子树。不能绕过父节点对 `hashclauses`、过滤条件等的检查。

需要同时看护：

- 普通 Hash Join 的探测侧和构建侧都能复用安全距离。
- Hash Right Anti Join 的 snapshot 构建侧可复用。
- 如果 Hash key 或 Join Filter 真正消费距离，仍然必须禁止近似复用。
- J1 修复必须同时生效；不能先放开 Hash 再把复合值漏判扩展到更多路径。

## 5. 未发现异常的已测边界

以下仅表示这些具体测试通过，不代表证明所有 SQL 均安全：

- 按 id 匹配的 Nested Loop、Merge Join、Hash Join 探测侧：返回相同的 8 个 ID，并实际使用近似结果。
- 按 id 的 Left Join：返回相同的 9 行；不存在匹配的 id=9 保留 NULL 距离，没有串入上一行距离。
- 按 id 的 Merge Anti Join：相同 6 行。
- 一对多 Nested Loop：重复匹配得到相同 4 行，没有错误去重。
- 直接消费距离、转换后消费距离、把 FLOAT8 距离传给 LATERAL：两种模式均返回相同 1 行，正确阻止了近似复用。
- 同时打开三个特性的 delta/snapshot/delete 视图：Merge Anti Join 情况两个 ANN 扫描都复用；Hash Right Anti Join 情况复现 J2，未出现额外结果错误。
- 当前对无关 FLOAT8 Join key 的保守拒绝是已知覆盖率限制，不另列为 BUG。

## 6. 现有回归为什么没有拦住

当前 `union_all_ann_feature_matrix.sql` 的 Join 新增看护集中于：

- 一条按 row_id 的 Merge Anti Join 正向 EXPLAIN。
- 一条直接 `q.distance < g.max_distance` 的负向 EXPLAIN。

这两条没有覆盖 RECORD/整行参数，也没有覆盖 ANN 作为 Hash 构建侧。更重要的是，这部分主要检查计划，没有为这些新边界加入“开关前后匹配行集不变”的执行断言。

修复后应把本次最小反例和 Hash 双侧正反例纳入现有 openGauss 回归框架，补 SQL 与 expected；不要通过接受新的错误 expected 来消除差异。近似排序的正向用例可按契约容许微小距离差异，但不消费距离的 Join 必须保持行数、重复数和 NULL 扩展语义；负向消费用例必须继续精确计算并保持结果集合。
