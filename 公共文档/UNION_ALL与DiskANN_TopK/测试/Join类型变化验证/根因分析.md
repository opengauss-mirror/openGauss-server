# UNION ALL 必需列裁剪引起 Anti Join 方向变化：实测与根因

## 1. 结论与适用范围

2026-09-10，在当前 openGauss 集成分支上，用 **63 行源数据**复现了：

```text
enable_union_all_required_columns_pushdown = off → Hash Anti Join
enable_union_all_required_columns_pushdown = on  → Hash Right Anti Join
```

主对照只切换上述开关；数据、统计信息、索引、SQL、work_mem 和其他参数不变。
Hash、Merge、Nested Loop 三种 Join 都开启，主 SQL 和主视图均没有 Hint。
`enable_union_all_diskann_topk_pushdown` 两边固定为 `on`。

本次复现的必要区分：

- **复现了只查询 `id` 的例子。** 根因是无用宽列被提前移出规划目标，改变 Hash 分批估算和候选成本，从而改变构建侧。
- **没有复现用户原来“查询 `id, val, title` 全部三列”的 Join 翻转。** 同数据同参数下，该形态两边都是 Hash Anti Join，行宽和 Join 成本相同，虽然 Subquery Scan 消除和 Merge Append 变化仍存在。
- 因而本报告证明“本特性可以改变 Join 方向”，**不等于已经定位了用户迁移分支那份三列计划的具体根因**。后者仍需要该分支的 DDL、数据/统计信息、会话参数及带成本的两份计划。

没有改动内核、原生回归文件或旧 ZIP。本次是专项实测，不是性能基准或全量回归。

## 4. 主 SQL 和实测计划差异

```sql
SELECT id
FROM topk_view_union
WHERE id BETWEEN 1 AND 5
ORDER BY val <-> '[1,0,0,0]'
LIMIT 3;
```

视图第一支为 `snapshot WHERE NOT EXISTS (delete)`，第二支为 alpha，以 UNION ALL 合并。

关闭必需列裁剪时，Join 子树如下（省略外围 Sort、Limit、Append 等节点及临时 schema 名；完整 verbose 见原始输出）：

```text
Hash Anti Join (cost=1.90..12.24 rows=1 width=4029)
  Output: s.doc_id, s.embedding, s.title, distance
  Hash Cond: (s.doc_id = x.row_id)
  -> Index Scan on topk_snapshot s (cost=0.00..10.33 rows=4 width=4029)
       Output: s.doc_id, s.embedding, s.title
       Index Cond: ((s.doc_id >= 1) AND (s.doc_id <= 5))
  -> Hash (cost=1.40..1.40 rows=40 width=4)
       -> Seq Scan on topk_deletes x
```

开启后：

```text
Hash Right Anti Join (cost=10.38..11.89 rows=1 width=25)
  Output: s.doc_id, distance
  Hash Cond: (x.row_id = s.doc_id)
  -> Seq Scan on topk_deletes x (cost=0.00..1.40 rows=40 width=4)
  -> Hash (cost=10.33..10.33 rows=4 width=25)
       Output: s.doc_id, s.embedding
       -> Index Scan on topk_snapshot s (cost=0.00..10.33 rows=4 width=25)
            Output: s.doc_id, s.embedding
            Index Cond: ((s.doc_id >= 1) AND (s.doc_id <= 5))
```

这里的 `distance` 只是上述摘录对向量距离表达式的简写，不是原始计划字段。
`rows=4` 是估算，不是实际输入数；snapshot 过滤后实际有 5 行。

两边 snapshot **都是同一个主键 Index Scan**，谓词、估算行数和扫描成本完全相同。因此不能把本例归因于 Seq Scan 改成 Index Scan，或 WHERE 选择率变化。

## 5. 根因链条：提前裁列 → Hash 分批估算变化 → 成本胜负反转

### 5.1 改写在路径选择前就改变了所需字段

关闭时，UNION 叶查询仍输出三列，snapshot 参与规划的宽度为：

```text
4 (id) + 21 (embedding) + 4004 (title) = 4029
```

开启时，title 既不属于最终输出，也不参与过滤、连接或排序，被从叶查询目标列中移除：

```text
4 (id) + 21 (embedding) = 25
```

embedding 仍是距离计算的必要输入，所以 Hash 构建子树保留它；不能把外层只输出 id 理解成源头连 embedding 也不需要。

此处不是事后把 EXPLAIN 的 Output 缩短：逻辑 Query 的目标列在关系和路径构造之前已经变窄，成本模型真正使用了变窄后的宽度。

### 5.2 两种 Anti Join 原本就都是合法候选

优化器会考虑：

- `Hash Anti Join`：snapshot 探测，以 delete 为 Hash 构建侧，返回没有匹配删除记录的 snapshot 行。
- `Hash Right Anti Join`：delete 探测，以 snapshot 为 Hash 构建侧，返回右侧 snapshot 中没有匹配的行。

交换的是物理左右位置和 Hash 构建侧，**没有把语义改为“返回未匹配的 delete 行”**。

### 5.3 DEBUG 日志确认了估算批数，而非只凭计划形状推测

固定观察右反连接候选，在同一 `work_mem=264kB` 下：

```text
OFF: ntuples 4, width 4029, workmem 264
     nbuckets: 128,   nbatch: 2
     Add seq page cost: startup_cost: 13.380000, run_cost: 6.500000

ON:  ntuples 4, width 25, workmem 264
     nbuckets: 32768, nbatch: 1
     无上述附加分批页成本
```

为什么只有几行也会碰到内存边界？本分支 Hash 估算有最少 32768 个桶；64 位桶指针本身约占 256 KiB，还要计入元组、对齐及 skew 预留。264 KiB 正好处于本例宽行/窄行候选的分批阈值附近，不需要大量数据。

**上述 nbatch 是规划器的估算。** 本次没有用 EXPLAIN ANALYZE 证明某个候选运行时实际写了多少临时文件，不能把估算分批写成已经观测到的真实落盘。

### 5.4 候选成本直接证明选择为什么改变

独立的 Leading Hint 视图仅用来显示候选，不用于主复现。两种候选的 Join 总成本为：

| 特性状态 | Hash Anti Join：Hash delete | Hash Right Anti Join：Hash snapshot | 无 Hint 主查询选中 |
|---|---:|---:|---|
| off | 12.24 | 19.89 | Hash Anti Join |
| on | 12.24 | 11.89 | Hash Right Anti Join |

右反连接候选的总成本精确日志约为 `19.888090 → 11.888090`。关闭时额外计入的分批页成本为 startup 加 3、run 加 5，总计 8；开启后消失。左反连接始终构建只有 row_id 的 delete Hash，其候选成本约 `12.241375`，没有变化。

因此，本例已经定位到“Hash 构建候选的宽度影响分批估算，继而改变总成本比较”这一层，而不只是泛泛地说“优化器觉得另一种更便宜”。

## 6. 反事实对照排除了什么

| 对照 | off | on | 支持的结论 |
|---|---|---|---|
| id；264kB | Hash Anti | Hash Right Anti | 主复现 |
| id、val、title；264kB | Hash Anti，width=4029 | Hash Anti，width=4029 | title 必需时不裁剪，不能套用宽度下降的解释 |
| id；512kB | Hash Right Anti | Hash Right Anti | 宽候选不再需要估算分批后，翻转消失 |
| 所有诊断后重跑主对照 | Hash Anti | Hash Right Anti | 同一会话内可重复，不是偶然一次计划 |

三列对照仍有 Subquery Scan 消除、Merge Append 变化，却没有 Join 翻转。它也直接否定了“只要 Subquery Scan 消除了，就一定改变 Join 方向”的因果说法。

## 7. 源码定位与阶段关系

以下路径相对工作树，行号对应本次实测时的文件。

1. `src/gausskernel/optimizer/plan/planner.cpp:1714`：首先执行必需列改写；1718 执行 Top-K；1729 执行排序键投影改写。这些发生在通用子查询拉平和关系/路径规划之前。
2. `src/gausskernel/optimizer/prep/preptopk.cpp:144`：`preprocess_union_all_required_columns()` 收集必需列，紧凑化 UNION 和叶查询目标列；成功后才安装复制的 Query 字段。
3. `src/gausskernel/optimizer/path/costsize.cpp:6853`：`set_rel_width()` 根据 `rel->reltarget->exprs` 累加列宽，不把表的全部物理列一概计入。
4. `src/gausskernel/optimizer/path/joinrels.cpp:767`：JOIN_ANTI 分支分别枚举 `JOIN_ANTI(rel1, rel2)` 和 `JOIN_RIGHT_ANTI(rel2, rel1)`。
5. `src/gausskernel/optimizer/path/costsize.cpp:4245`：`initial_cost_hashjoin()` 获取输入行数/宽度，调用 Hash 内存估算；`numbatches > 1` 时增加页读写成本。
6. `src/gausskernel/runtime/executor/nodeHash.cpp:560`：`ExecChooseHashTableSize()` 同时供规划器使用。这里出现于 executor 源文件，**不意味着此次日志来自查询执行阶段**。664 起设置最少桶数并判断是否分批。
7. `src/gausskernel/optimizer/path/costsize.cpp:4506`：`final_cost_hashjoin()` 进一步计入匹配、额外条件等 CPU 成本，形成候选总成本。
8. `src/gausskernel/optimizer/plan/createplan.cpp:1582`：禁止物理全列 targetlist 回填，是物理计划阶段的保护；它本身不是倒过来改变先前 Join 路径选择的入口。
9. `src/gausskernel/optimizer/plan/setrefs.cpp:1459`：`trivial_subqueryscan()` 在更晚阶段判断能否去掉直通包装；targetlist 等长只是条件之一。这里同样不是 Join 枚举/成本选择入口。

正确的主因顺序是：

```text
早期 Query 目标列裁剪
  → RelOptInfo / Path 使用窄行宽
  → Hash 候选分批估算和成本变化
  → 选中另一构建侧
  → 创建物理计划、后续消除可直通的 Subquery Scan
```

不能写成“Subquery Scan 先消除，然后才导致 Join 翻转”。
