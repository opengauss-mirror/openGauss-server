## 普通字段与 B-tree 的代码核对

这不是仅根据 SQL 拼写作出的结论。对覆盖索引阶段末 `d98de98c80` 与原特性前 `8dea19a42a` 源码，沿 DDL、构建、资格执行核对：

- `diskannhandler` 的 `amcanmulticol=false`；`indexcmds.cpp` 对多个 key 检查该能力并拒绝。旧覆盖实现只放行单个 vector key 的 INCLUDE payload。
- `InsertVectorIntoPage` 接收 vector key 与 INCLUDE 值，写入同一个 DiskANN 索引元组；没有构造第二棵普通 B-tree。
- `AnnIndexBuildFilterDesc` 把表字段映射到索引属性；过滤器用 `index_getattr` 读 payload，再调用比较函数判断。它没有调用 B-tree 来检查普通字段。

[旧代码原文、提交及行号](evidence/remove-covering-index-20261011/old-code-multikey-and-filter-trace.json)保留上述证据。当前隔离库实测 `USING diskann(v, bucket)` 拒绝；不写 USING 的 `(v, bucket)` 可以创建，但 catalog 显示整个索引为普通 B-tree，距离查询仍需 Sort。[实际 DDL 与 catalog](evidence/remove-covering-index-20261011/multikey-ddl-confirmation.json)保存 SQLSTATE、实际索引类型和计划。

结论限定于本仓这些版本的 DiskANN：没有“普通字段自动建 B-tree，再与向量索引形成中过滤”的能力；旧 INCLUDE 过滤器和当前新的资格 SubPlan 是不同实现。

## Bitmap 与旧版本过滤能力

旧 `8dea19a42a` 的 `pg_am.h` 中 DiskANN 的 `amgetbitmap` 为空，handler 也未注册该接口。普通 `Bitmap Index Scan` 调用 `scan_handler_idx_getbitmap` 生成 TID 位图，`BitmapAnd` 使用 `MultiExecProcNode` 取各子位图求交；优化器只把 `amhasgetbitmap` 成立的索引加入 Bitmap 候选。除此之外，旧 ANN 执行器和 DiskANN 搜索没有消费普通 Bitmap 作为图内资格检查的接口。代码中的分区报错字符串含有 “bitmap index scans”，不代表存在该数据流。

因此本仓旧版本不存在“普通 Bitmap 与 DiskANN 图搜索形成中过滤”的执行关系。已移除的覆盖索引实现曾按 INCLUDE payload 做中过滤；移除后用于性能对照的原生 DiskANN 路线先取候选、再回表执行普通条件，属于后过滤。普通 `Bitmap Heap Scan → Sort → Limit` 可以先按普通条件筛选再算距离，但不经过 DiskANN，不能计作 ANN 前过滤。

## 初版历史：AUTO 与新老能力的边界（后续已修正）

关闭 `enable_diskann_filter` 时新版本沿用旧 ANN 路径；开启时，`indxpath.cpp` 把原 ANN 路径交给 `ann_preserve_filter_candidate` 保存为派生模板，`ann_choose_complete_route` 比较新 PRE/IN/POST 和普通关系路径，原 ANN 后过滤没有作为独立候选放回最终比较。新 POST 的固定候选搜索协议也不等于旧扫描的补批协议。这是当前实现事实，不能据“功能保留”宣称“旧方案仍参与 AUTO”或“代价准确时一定不退化”。
