## 2. 已实现行为

| 范围 | 实际实现 |
|---|---|
| 单表 PRE | 原生 Ann Index Scan 的资格子树消费到 EOF，仅保存合法目标 TID 集合；Seal 后进入图搜索，最终普通 Sort/Limit 使用原 SQL 距离 |
| 单表 IN | 图搜索每个候选在索引内容锁释放后同步执行真实资格 SubPlan；同一扫描周期缓存资格结果，独立 slot/ExprContext |
| POST | ANN 候选向上交给普通残余条件和输出 Join，再由普通 Sort/Limit 截取完整业务结果 |
| Join 组合 | 保留普通候选路径，按完整资格关系域派生 PRE/IN 和普通 ANN 输出 Join 路线，原生 Join 合法性检查继续生效 |
| 多条业务匹配 | 只按真实目标身份去重候选；同一目标匹配的全部业务行仍由输出 Join 形成，K 计算最终业务行数 |
| NL 内侧 | 不要求目标或业务关系唯一；真实 ReScan 重置 epoch，原生 Material/Sort 重放保留重复外侧匹配；相关与独立查询块分别验证 |
| 行身份与快照 | AStore MVCC/HOT 根身份和当前向量 key 验证；资格与输出共用同一 EState 语句快照 |
| 计划与成本 | 扩展现有 IndexPath/Ann Index Scan 及计划字段传递，资格私有投影按实际需要收窄，成本复用原生子路径并计入预计候选检查次数 |

没有新增 VectorFilterScan、VectorFilterBuild 或 Custom Scan 执行节点。没有备用普通 Exact PlanState。前两个阶段按一次配置的搜索预算执行；相关 NL 可有多个真实扫描周期，每个周期一次搜索，累计 Search Rounds 按 Scan Epoch 核验。

目标节点被父 Hash Join 空输入短路时，计划明确显示 NOT STARTED；这与 PRE 自己进入搜索后判定空资格不同。未启动节点不能作为“PRE 跳过图搜索”的证明。

本次涉及 DiskANN 查询读取和既有扫描接口，不修改 AStore 页格式、系统目录、WAL、DML/VACUUM 或事务协议。另修复既有 DiskANN 图剪枝距离类型未初始化问题；不能据此声称旧错误图自动修复，相关隔离对象重建后验证。迁移其他同源仓仍须先实测其 DiskANN 内部排序/补批行为和 AStore/UStore 类型，再制定迁移方案。

## 4. 性能数据与测量口径

最终质量矩阵共 504 个配置、每个 PRE/IN/POST/AUTO 四种模式，共 2,016 条记录和 2,018 项有效性/排序检查。N=50,000/100,000、D=8/768、L2/COSINE、过滤保留 0/0.1/1/10/50/100%、独立/正相关/负相关；另有 8,192 行、每个相同向量 8 个目标身份、业务匹配倍数 1/4 的配置。

目标向量由第一坐标 `1+i/N`、其余坐标 `0.1` 构成，是合成一维几何；正文交替 16/2,048 字节 PLAIN。正式 Join 使用存储列 `d.id=a.target_id`，业务 payload 为 16/128 字节，初始化桶值显式 floor 后验证为 0..999。原 P1 目标数据和八个 DiskANN 索引原样复用；重复向量对象的原查询 K=32 不用于改写任何 Oracle K=10 查询。见[数据清单](执行包/evidence/V-02-P2/final-performance-fixtures/dataset_manifest.json)。

典型 SQL 先按覆盖选定：Q00 无过滤控制、Q01 单表弱过滤、Q02 单表正相关强过滤、Q03 单表独立强过滤、Q04 Join 强过滤、Q05 Join 弱过滤、Q06 重复向量和多业务匹配、Q07 向量扫描处于 NL 内侧的非唯一原查询。另在正式对测计时前补 Q08：10 万目标、768 维、每目标 4 条业务匹配的新性能 SQL，初始合同为 K=32。Q00～Q07 和全部 Oracle 原 SQL/K 保持原样。实际查询见[八条典型 SQL](执行包/sql/前两阶段特性前后性能典型SQL.sql)与[高维多匹配 SQL](执行包/sql/前两阶段高维多匹配性能SQL.sql)。

每条先记录旧版本原生默认计划与新版本 AUTO/PRE/IN/POST 的完整投影结果、实际行数和普通 Exact 参考。按同一候选预算序列，选择首个两版本都与完整参考多重集严格相等的配置，再计时；不满足的配置保留质量差异，不作速度提升依据。AUTO 单列，强制模式单列，不能把后者的收益当成自动选路收益。

正式 ABBA 的 A 是旧二进制、B 是当前二进制。每个窗口正常停止旧实例、通过统一脚本启动指定二进制，核验实际版本、预热 10 秒、测量 30 秒；只有一个实例访问数据目录。切换发生在 SQL 执行之间，不是特性在一次执行中更换计划。两版本使用同一静态已提交数据集；每个窗口内部用一个只读 RR 快照，每次查询校验原投影完整 Counter。不同二进制的执行不能共用同一个内存快照指针。任何 swap-in/out 或 major fault 均整批排除重跑。

测试为单客户端闭环、Unix socket、query_dop=1、热 OS 缓存、work_mem=128MB、新版本过滤内存预算 128MB。矩阵固定 probes=256；典型 SQL 的实际共同预算由两版本质量核验确定，并在每行列出。SQL execute+fetch 是时延计时范围；Counter 校验在该范围外，闭环 QPS 的总时间包含校验。热 OS 缓存不等于所有页都在数据库 shared_buffers 内。

正式接受 20 个完整 ABBA 批次、80 个窗口，排除 6 个污染批次；接受窗口共完成 **460,817 次查询**，每次原投影完整多重集均相等。完整 P50/P95/P99/QPS、逐窗口工作量、内存及实际计划见[正式汇总](执行包/evidence/V-02-P2/actual-before-after-summary/实际前后版本性能与质量汇总.md)，原始数据见[真实前后版本计时](执行包/evidence/V-02-P2/formal-real-before-after/measurements.json)。

显式 POST 在单表弱过滤、业务 Join 弱过滤、高维四业务匹配中分别达到 **10.599 / 20.660 / 36.202 倍** P50 提升；显式 IN 在独立单表强过滤和高维四匹配中分别达到 **2.574 / 5.784 倍**。这些比较的两端完整结果均相等。

显式模式也有明显退化：Join 强过滤 PRE 为 2.520→222.984 ms、IN 为 2.632→65.671 ms；NL IN 为 0.744→149.114 ms；高维四匹配 PRE 为 488.821→1688.843 ms。普通计划已经很快、资格构建昂贵或需要多次扫描时，不应仅因支持 ANN 就强制选择它。后续应优化自动选路和额外开销；本报告不据此修改已冻结实现或原 SQL。

实际工作量可以解释模式之间的差距，但不作为逐函数耗时归因：Q04 PRE 的资格 Hash Join 先扫描 100000 条目标行才得到 1000 条资格源行；Q08 PRE 消费400000条资格源行。Q08 IN执行8166次真实资格Probe，只交付256个目标给输出Join；Q08 POST没有资格Probe，仅对256个候选做可见性/向量key读取，输出Join保留1024条业务匹配后再取32条。原NL IN确实有6个扫描周期、累计38622次Probe。

Filter Memory Peak 在这些显式模式中约0.85～6.81MiB；Q08资格Hash为5321kB、输出Hash为1294kB、最终Top-N Sort为92kB。整实例VmRSS峰值另列于正式汇总，不能把它当作查询私有内存。源/输出读取和Buf命中含父子包含关系，不相加；AStore Fetch Attempts不计资格源TID转换和普通输出Join的全部读取。

固定预算的质量矩阵不能作全域质量达标声明。PRE/IN 的非空不足 K 比例为 P1 17.5%、P2 12.67%；POST 为 P1 40%、P2 36.67%。上表 Recall 均值是配置等权且受单预算、相关性与业务并列边界影响；正式性能表只使用计时前已满足严格完整结果相等的共同预算，不按时延筛选配置。

空域有独立记录：P1 每模式 24 组空域，P2 每模式 60 组。P2 PRE/POST 的空父 Join 可以短路 ANN（NOT STARTED）；这不能证明 PRE 自己会跳过图搜索，也不能混入非空不足 K 比例。

## 5. 环境与结果边界

主机约 8 GB 内存。早期相对 Exact 的尝试因其他驻留进程换页/major fault 多次作废；用户明确主基线后，该轮主动中止，原始窗口保留为诊断。其已通过的单表配对也不混入“相对特性前”的最终统计。缓存预热不保存任何进程页内容；正式轮临时调整 vm.swappiness，并在结束或异常时恢复。测量时不同时编译、运行 gdb、Oracle、Milvus 或其他 SQL 测试。

图搜索 budget 固定，因此质量矩阵的合法性和排序检查通过不代表全域 Recall=1；不足 K 和 Recall 将原样列入最终表格。不同向量的多个目标身份不合并，同目标业务匹配不去重。Raw EXPLAIN 的工作量与正式客户端时延分别保存；AStore Fetch Attempts 只计资格回调的可见性/HOT/key 读取，不代表普通 Tid Scan、最终回表和业务 Join 的全部读取。

整个 gaussdb 的 VmRSS 不能当成单查询私有峰值，Filter、Hash、Sort 内存和临时文件分别核验。当前测量不支持真实 embedding、冷态、多客户端吞吐、老化图或 DML 时延性能结论。
